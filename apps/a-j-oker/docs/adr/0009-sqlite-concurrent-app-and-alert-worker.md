# SQLite 读写并发与事务开始等待

应用、Payload 后台和飞书提醒任务共享本机 SQLite 文件。原 DELETE 日志模式使另一连接的提交锁阻塞查询；默认立即抛错，用户受理记录接口会返回通用500。真实后台日志记录了 SQLITE_BUSY，隔离回归也连续复现了相同接口错误。

启用适配器的 WAL，保持 FULL 同步。查询可在写入时读取一致的已提交数据；仍只有一个写入者。所有本地客户端仅在 BEGIN 尚未成功时异步等待，最多2秒，让同进程持锁请求有机会结束。事务正文、提交以及外部通知不自动重放；既有提交失败传播与不确定发送结果停止重发的规则不变。

当前 @libsql/client 0.18.0 会把 BEGIN 失败的原生连接放回池中，随后提交可报“SQL statements in progress”。补丁只丢弃这一条未成功开始事务的连接，避免将残留语句带入下一次事务；升级驱动时须保留回归检查或移除已由上游修复的补丁。

备份使用 SQLite backup API，不能直接复制运行中的主数据库文件；现有 privacy-snapshot 检查覆盖 WAL 已提交页与恢复。切换版本前停止应用和提醒写入者，完成可校验备份后再启动；回滚应用时不回卷已写入的数据。

HTTP 与提醒任务故障仅记录固定错误类别和时间，不输出异常原文、SQL参数、用户输入或凭据。历史提醒延迟缺少原始错误类别，不能仅凭此复现宣称历史每次失败均同根。

验证：真实认证的受理记录接口、独立线程短暂持锁、同事件循环写锁释放、超时无部分写入及恢复、独立进程50轮提醒与50次用户查询/后台处置、不确定发送不重试、WAL备份恢复。隔离验证不代替部署后的真机和持续运行验收。
