# 飞书危机提醒接入与验收

「赢麻的阿 J 先生」的紧急案件通过飞书群「阿 J 安全值守」提醒负责人孙逢。群内只保留负责人及专用通知机器人。通知正文仅含固定提醒、随机案件编号和需要登录的后台入口，不包含用户原话、身份资料或紧急联系人电话。

2026-10-24 已在飞书网页版创建群组，成员为孙逢一人。机器人配置、手机收件确认及服务端启用尚未完成；当前不能在审批材料中写成已经实现自动到人通知。本地实现与模拟验收不替代实际送达演练。

## 接入步骤

1. 在群设置的群机器人中添加专用自定义机器人，名称用「阿 J 安全提醒」。开启签名校验；不添加聊天读取权限或无关成员。网页版如未显示添加入口，使用飞书客户端。
2. 将机器人 Webhook 和签名密钥保存到服务端私有配置文件，权限设为 0600，不写入仓库、截图、审批材料或日志。配置变量为 `HELLO_FEISHU_WEBHOOK`、`HELLO_FEISHU_SIGNING_SECRET`、`HELLO_FEISHU_ALERTS_ENABLED=false`；`HELLO_ORIGIN` 使用真实后台的 HTTPS 根地址。仅接受 `open.feishu.cn` 的标准自定义机器人地址。
3. 备份目标数据库并按现有部署流程执行迁移 `20261024_120000_feishu_alerts`。应用和通知任务必须使用相同的数据库、稳定的 Payload 密钥和飞书配置。迁移不会为历史案件自动排队群发。
4. 运行 `node --import tsx scripts/feishu-alerts.ts --send-test`。该操作确实向群里发送一条标为“无真实危机事件”的合成测试消息；输出测试编号及平台接收结果。CLI 不自动读取环境文件，应由进程管理器注入私有配置，或在本机使用 Node 的 `--env-file` 参数。
5. 由负责人在手机飞书核对该编号并确认能收到提醒，在一小时内运行 `--confirm-test <该编号>` 登记本人确认。平台成功响应不能代替这一步。检查该群未免打扰、@所有人通知及手机系统推送可用。
6. 将启用变量改为 `true`，重启应用并常驻运行 `--worker`。部署可在原 Compose 文件上叠加 `deploy/compose.feishu.yml`，显式选择 `feishu` profile。未配置或未确认时任务不会发送真实案件。
7. 使用专门合成案件演练“建案—群提醒—手机收到—后台领取—登记联系结果”；清楚标注测试，保留结果。生产案件仍由负责人主动领取并处置。

部署命令示例（先完成上述配置与确认）：

```sh
docker compose -f deploy/compose.preview.yml -f deploy/compose.feishu.yml --profile feishu up -d app feishu-alerts
```

## 发送和故障处理

新建紧急案件时，在同一事务内记入通知队列。单一常驻任务每 2 秒检查一次，使用 30 秒数据库租约避免争抢；发送间隔至少 2 秒。网络调用不占用数据库事务。配置变更后须重新测试及确认。

仅服务端明确拒绝的限流最多尝试 5 次，间隔为 15 秒、60 秒、180 秒、600 秒。网络超时、无效回执、HTTP 5xx 可能在成功发送之后发生，均停止自动重试，保留错误供人工核对。签名或权限等永久错误直接标记失败。超过 24 小时、已经领取、已经处理或已降为普通案件时停止自动提醒。重启后恢复数据库中的待发记录；进程中途退出留下的 sending 记录在租约到期后标记 delivery_uncertain，不再次外发。错误状态和尝试次数在案件后台保留。

Webhook 没有端到端幂等确认：平台已经接收但响应丢失时，不能判断是否送达。因此不确定结果必须由人工核对，不自动重发，也不伪装成已送达。当前不支持自动电话或短信加急，也不以网页或手机“在线”推断负责人已经看到消息。

后台分开记录“平台已接收”“人工领取”“实际联络结果”。工作任务超过 30 秒未更新状态、配置失效或有发送错误时，不再显示通知正常。检查失败案件并使用已确认电话人工联络；后台的健康标志本身不是独立的故障呼叫服务。

## 验收与证据

常驻任务必须检查持续运行和异常退出，不能只凭一次新心跳通过。旧的 `@libsql/client@0.14.0` / `libsql@0.4.7` 组合在 Linux 预览镜像中出现连接数随事务增长及退出码 139；隔离的原生驱动循环也能复现。根目录将 Payload 3.85.1 的 SQLite 客户端固定到 `0.18.0`，应用显式原生驱动同步固定为 `0.5.29`。该覆盖也作用于官网的 SQLite 适配器，需一并验证兼容性；不改变数据库文件、表结构或业务权限。

`pnpm test:sqlite-connections` 在独立临时数据库中执行 1000 次提交、回滚和关闭，核对持久化结果、Linux 连接数不持续增长及子进程正常退出。CI 同时运行通知队列集成检查；部署后仍须验证真实工作进程持续更新心跳且没有异常重启。后续移除版本覆盖时保留这两项回归，不以仅升级版本号代替验证。

`scripts/feishu-alerts-check.ts` 使用隔离 SQLite 和模拟发送器，禁止真实网络，覆盖重复迁移与旧数据保留、事务回滚、确认门槛、持久化重试、次数上限、进程实例重建、不确定发送停止、同一连接及两个独立进程并发去重、配置变化及权限边界。`src/operations/feishu.test.ts` 检查签名向量、地址限制、无敏感正文以及飞书错误响应处理。跨主机故障和真实移动端推送必须在部署环境另行演练。

接口及签名依据：[飞书自定义机器人官方文档](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)。

2026-10-29 真机合成案件暴露了另一类故障：Payload 3.85.1 的事务包装吞掉提交异常，发送完成日志与实际数据库不一致。根目录补丁 `patches/@payloadcms__drizzle@3.85.1.patch` 将开始/提交失败传回调用者，同时保留显式回滚语义；影响本工作区使用该版本的适配器。通知发送前、完成后分别在事务外回读持久状态。`scripts/transaction-failure-check.ts` 覆盖提交故障、开始失败、正常回滚恢复，以及发送后落库失败再启动不重发。升级上游移除补丁前必须保留这些回归。该补丁及离线检查不能替代实际环境案件演练；真实工作任务在修复验证完成前保持停止。
