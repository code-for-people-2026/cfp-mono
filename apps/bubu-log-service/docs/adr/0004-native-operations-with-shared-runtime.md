# 原生运营后台共享业务进程，事实修改仍通过 MCP

#397 使用原生 Payload Admin，并在首页挂载按宝宝组织的最小运营工作区。原有身份、录入与私人对话集合继续由同一个 `Store` 保存；仅新增 `ops-users` 账号及 `ops-requests` 命令回执。旧 Payload 自动创建的 `users` 表保留但拒绝访问，避免升级时删除历史表。#398 的会员状态和策略通过注入接口提供，运营不预设价格、体验期限或到期停服。

Next/Payload 的管理路由由现有 Node 入口承载。全局运行实例及 Payload 默认缓存确保只有一个 Payload、IdentityService、RecordsService、CollectorService、AttachmentService 和 ChatService。独立 `next start` 不能初始化另一业务实例。数据库目录的进程锁同时保护服务、首位管理员初始化及离线运营 CLI；共享数据库事务队列也覆盖原生 Payload 登录和 CRUD，避免与业务事务争用 SQLite。多进程和多主机部署不在此方案内。

`ops-users` 与照护身份彻底分开，角色及宝宝范围在每次请求和每次委托授权时从数据库重读。短期委托具有稳定的运营操作者 ID；请求恢复不依赖一次性的会话 ID。审计只读角色看安全摘要，敏感事实、来源、修订、附件正文要求有写权限的人工运营填写理由并先落审计。原生照护集合只有只读摘要；原始 JSON、会话、凭证、私人对话均不可通过 REST 或 Admin 编辑或导出。GraphQL 关闭。

照护变更通过真实 loopback MCP，复用记录版本、修订、待补、统计和投影恢复。查询复用统一读模型，包含尚未产生 sidecar 行的旧 Activity。UI 保留开始编辑时的版本，刷新不会把旧输入套在新版本上；人工重新选择版本会清空旧输入。CMS 人工委托可关闭待补照片，但仍须真实上传、版本化关联或明确“不知道”；采集与普通离线 operator 凭证不能代替人工确认。

身份／授权／群配置动作和审计、回执在同一重入事务内提交；MCP 调用不持有外层事务，避免回环死锁。跨旧库写入使用既有持久操作及相同请求号恢复，回执仅存 ID、版本与状态，不复制照护事实。邀请码和采集凭证仅在首次响应返回明文，重试只报告已经签发，不能恢复明文。邀请码的签发委托保留到邀请到期，接受时仍重查运营账号权限。

旧服务的并发写入窗口、公开历史照片和真实迁移验证仍遵循 ADR-0002。后台的合成环境验收不能证明真实客户迁移完成，也不会自动开启采集或支付。
