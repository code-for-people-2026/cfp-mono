# Kith Inn 社区供餐小程序 PRD

> 版本：v0.1
> 状态：讨论稿
> 更新时间：2026-08-03

## 1. 产品概述

Kith Inn 是一款服务于社区小规模供餐者及其邻里顾客的微信小程序。

第一阶段以“桃子”为核心样本：她在为自己家庭做饭的同时，为本小区及周边小区的邻居增加若干份固定套餐，并自行配送。Kith Inn 帮助她完成菜品维护、周菜单规划、餐次开放、订单汇总、配送履约和收款状态记录；顾客则通过微信分享入口查看菜单并下单。

## 2. 背景与问题

桃子目前主要依赖微信群文案、群接龙、私聊和个人记忆经营：

1. 每天决定做什么菜耗时，希望从自己会做的菜中一次规划一周菜单。
2. 顾客可能通过群接龙、私聊或未来连续订餐约定表达需求，下单来源分散且容易遗漏。
3. 备餐份数、顾客份数和配送地址依赖聊天记录与记忆，履约效率低。
4. 配送进度和收款状态没有统一记录，容易漏送或漏收款。

## 3. 产品目标

- 将桃子会做的餐品沉淀为可维护的菜品池。
- 帮助桃子生成并调整一周菜单，减少日常排菜负担。
- 将顾客自助下单、私聊代下单和订餐约定生成的订单统一为结构化订单。
- 让桃子随时知道每个餐次需要做多少份、分别送给谁、送到哪里。
- 分开管理履约状态和收款状态，降低漏送与漏收款概率。
- 让受邀顾客能够从微信分享入口查看菜单，并在首次获得桃子确认后持续自助下单。

## 4. 第一版非目标

- 小程序内付款、退款、分账和平台抽佣。
- 配送路线规划、路线排序和预计送达时间。
- 顾客口味备注、菜品选择或个性化套餐。
- 菜谱步骤、食材克数、采购、库存、成本和营养管理。
- 菜品照片。
- 商家发现、店铺列表、评价和社交功能。
- 面向多类商家的通用经营系统。

## 5. 用户角色

### 5.1 供餐者

以桃子为代表的小规模社区供餐者，负责维护菜品、规划菜单、开放餐次、接单、备餐、配送和记录收款。

### 5.2 顾客

来自本小区或周边小区的邻居，从桃子在微信群或私聊中的分享进入小程序。顾客首次获得桃子确认后，可以持续查看开放餐次并下单。

## 6. 核心概念

### 6.1 餐品

桃子会制作的一道荤菜、素菜或汤。餐品具有名称、类型、主料、排菜属性和启停状态。

### 6.2 周菜单

桃子对一周午餐和晚餐的内部计划。周菜单不代表相应餐次已经开放预订。

### 6.3 餐次

某一天的午餐或晚餐，是供餐和接单的核心单位。一个餐次包含菜单、固定单价、接单截止规则、餐次容量及关联订单。每个日期的午餐和晚餐都在餐次日历中独立存在，桃子可以分别安排和开放。

### 6.4 订单

某个餐次下的一笔份数记录。顾客订单、桃子代下订单、订餐约定生成的订单和桃子自家用餐均以订单形式进入餐次总份数。P0 中，同一顾客在同一餐次至多有一笔有效订单；追加需求直接调整这笔订单的份数，不再创建第二笔订单。

### 6.5 顾客关系与首单申请

顾客关系连接一个用户账户与一个商家。用户通过商家分享进入，但只有获得商家确认后才成为该商家的已确认顾客。尚未确认的用户首次提交的是首单申请，不是订单，也不占用餐次容量。

### 6.6 订餐约定

桃子维护的未来订餐规则，可以来自顾客私聊达成的约定，也可以记录桃子自家用餐需要。订餐约定不是订单、不涉及自动扣款，需要在实际开放的餐次中经桃子确认后生成普通订单。

## 7. 产品能力

### 7.1 菜品池

- 支持通过自然语言一次录入一道或多道餐品。
- 系统辅助识别餐品类型、主料和排菜属性，桃子确认后保存。
- 支持搜索、筛选、编辑、停用和彻底删除。
- 停用餐品不再参与排菜，但可以恢复。
- 餐品停用后才允许彻底删除；历史菜单保留当时的餐品信息。

### 7.2 周菜单规划

- 当前套餐固定为每人每份 2 荤、2 素、1 汤，所有顾客收到相同套餐。
- 默认对本周全部 14 个午晚餐次排菜；已经明确设为不供餐的餐次不参与。
- 菜单生成后再将某个餐次设为不供餐，不触发其他餐次重排，原菜单仅在商家端保留。
- P0 不要求桃子先描述排菜规则；系统按照内置规则和带权随机选择，一键生成可编辑的周菜单草稿。
- 固定套餐组成、只使用启用餐品和同餐不重复菜品属于硬规则；午晚餐及相邻餐次尽量不重复主料、每餐尽量不超过一道费工菜属于默认软规则。
- “费工”是否值得作为独立餐品属性和默认排菜规则尚未得到真实使用验证；P0 讨论稿暂时保留，并在原型中验证桃子是否愿意维护该属性，以及“换一道”是否已经足以处理制作复杂度问题。
- 每个餐次仍自动排一份汤；汤允许更频繁重复，默认不参与主料重复限制。
- 硬规则无法满足时，系统不静默违反规则，应展示已完成部分和冲突原因；只有软规则无法全部满足时，可以生成完整菜单并标出被放宽的规则。
- 每道菜提供“换一道”，立即随机替换为同类型的另一个启用餐品，其他菜保持不变。连续换菜时，在候选用尽前不再次出现刚刚被换掉的菜。
- 桃子不满意随机结果时，可以直接从同类型菜品池选择目标餐品；P0 不提供换菜撤销。
- 随机替换和手动选择都不得破坏硬规则；手动选择可以覆盖软规则，但需要显示相应提示。

未来如需支持不同套餐组成，可以将“2 荤、2 素、1 汤”扩展为商家可配置的餐次内容模板；自然语言描述本周偏好或特殊排菜要求也作为后续验证方向，第一版均不实现。

### 7.3 餐次开放与分享

- 餐次日历按日期展示午餐和晚餐，桃子可以从今天向前或向后查看近期记录和未来安排；系统不限制只能开放第二天的餐次。
- 餐次默认为“待安排”，顾客端显示“尚未开放”；桃子明确不做时可以提前设为“不供餐”，顾客端显示“本餐次不供餐”。
- 周菜单和餐次开放相互独立。待安排或不供餐餐次的菜单仅在商家端可见，顾客不能查看菜单或下单。
- 桃子根据实际安排逐个开放餐次。开放前必须确认准确日期、午餐或晚餐、菜单、价格、截止规则和餐次容量。
- 系统提供商家级的“午餐默认截止规则”和“晚餐默认截止规则”，具体值由桃子统一设置，格式为“餐次前一天／餐次当天 + 具体钟点”。
- 每个餐次自动继承对应餐别的默认规则；开放餐次时，系统将其换算为完整日期时间，桃子可以仅修改本餐次的具体截止日期和时间作为覆盖值。
- 修改商家默认规则影响之后尚未开放且没有单独覆盖的餐次，不追溯修改已经开放或已经单独调整的餐次。
- 商家端、开放确认页和顾客端均展示完整日期、星期和钟点，并辅以“餐次前一天／当天”说明，避免“晚上11点”等模糊表达。
- 开放操作需要二次确认，确认信息必须明确显示日期、星期和午餐或晚餐；开放后顾客才能查看菜单，是否可以下单还取决于剩余容量、截止时间和桃子是否主动停止接单。
- 系统提供一个午餐、晚餐共用的商家默认容量，由桃子设置；每个餐次自动继承并可以单独调整，修改默认容量不追溯影响已开放或已覆盖的餐次。
- 餐次容量包含顾客自助订单、桃子代下订单、顾客订餐约定生成的订单和自家订单。顾客端剩余份数为餐次容量减去当前有效总份数，最低显示为0。
- 顾客端展示准确的剩余份数。
- 订餐约定将生成的顾客订单与自家订单达到或超过餐次容量时，系统警告桃子但仍允许开放；顾客端显示“已满”，不能继续下单。
- 桃子调整容量或取消订单后，如果重新出现剩余份数，且餐次尚未截止或主动停止接单，顾客端恢复可下单。
- 达到餐次容量、截止时间或桃子主动停止接单后，顾客不能继续下单，但已有订单不受影响。
- 曾经开放的菜单在停止接单、配送和完成后继续保留，供顾客和桃子查询历史；取消餐次也保留原菜单与变更记录。
- “不供餐”只用于从未开放的餐次；已经开放后决定不再履约时使用“已取消”，并处理关联订单和顾客通知。
- 桃子始终可以手动加单；超出餐次容量时系统提示确认。
- 支持分享某一天的已开放菜单，也支持分享单个餐次。
- 餐次分享卡片直接进入对应日期和餐次；已确认顾客也可以直接打开小程序，从餐次日历找到最近开放的餐次。
- 桃子的菜单分享同时承担商家邀请入口；平台不提供公开商家发现或搜索列表。

### 7.4 顾客下单

- 顾客通过桃子的菜单分享进入并查看餐次；没有桃子邀请或既有顾客关系的用户，不能通过搜索小程序发现桃子或向她下单。
- 具有有效邀请或既有顾客关系的顾客可以在餐次日历中查看近期记录和未来供餐状态；只有处于开放预订状态的餐次展示菜单并允许自助下单。
- 顾客在需要提交时通过微信授权登录，系统据此识别同一小程序账户，但不将微信登录等同于桃子已经确认其顾客身份。
- 尚未获得桃子确认的用户选择份数和地址后提交首单申请，并将申请卡片分享到与桃子的微信私聊。首单申请不是订单，不生成订单编号、不进入制作份数，也不占用剩余容量。
- 桃子在微信中识别发送者后，可以在商家端确认顾客关系并接受首单申请；接受后才生成正式订单。如果此时餐次已经截止或满单，桃子按商家手动加单规则决定是否继续。
- 已确认顾客选择份数和地址后提交订单；满足截止和容量条件时订单立即确认，不需要桃子逐单审批。
- 每笔订单生成一个短且易读的订单编号，线下付款核对复用该订单编号，不再生成独立对账码。
- 下单成功页引导顾客复制或分享不含详细地址的订单摘要，并回到与桃子的微信聊天中完成付款。
- 桃子可以拒绝首单申请或停用顾客关系；被停用的用户不能继续向桃子下单。
- 同一天午餐和晚餐分别形成订单。
- 顾客可以查看自己的订单，包括已关联到自己的桃子代下订单。
- 桃子代下订单显示“商家代下单”标记。

### 7.5 地址

- 顾客拥有并维护自己的地址簿，可以保存多个地址和默认地址。
- 每个地址的收餐人称呼、小区和联系电话必填，楼栋号和门牌号均为可选项。
- 联系电话属于履约信息，不作为 P0 的登录账号，也不要求通过手机号完成登录。
- 桃子可以为订单选择地址，但不能新增、编辑或删除与顾客账号绑定的地址。
- 订单保存下单时的地址快照，顾客之后修改地址簿不影响已有订单。
- 订餐约定保存独立的地址快照：桃子可以从顾客地址簿选择后复制，也可以临时填写；两种方式都不修改顾客地址簿。

### 7.6 桃子代下订单与订餐约定

- 桃子可以为已有顾客或临时顾客手动添加订单。
- 如果该顾客在所选餐次已经有有效订单，系统展示原订单并让桃子调整份数，而不是再创建一笔订单。
- 手动订单不受顾客端截止和剩余份数限制。
- 桃子可以创建没有登录手机号的临时顾客，但为其代下订单时仍需填写本单的收餐联系电话。
- 订餐约定只由桃子创建和维护；顾客约定来自顾客私聊，自家约定来自桃子自己的用餐需要，顾客端不提供建立或修改入口。
- 由于使用低频，P0 从顾客详情提供建立和维护入口，不占用商家首页主导航；完成一次代下单后可以提供弱提示入口。
- 订餐约定使用简单的连续日期范围：从某天开始，到某天结束或不设结束日期，并指定午餐、晚餐或两者及各餐别默认份数；顾客订餐约定还需保存配送地址。
- 顾客地址簿之后的修改不自动改变订餐约定；桃子修改约定地址只影响之后生成的订单。生成订单时，订单复制约定当时的地址作为自身地址快照。
- 第一版不支持按不同星期组合、自然语言规则或其他复杂周期。
- 同一顾客、同一餐别不能存在有效期重叠且尚未结束的订餐约定；发生冲突时引导桃子修改原约定，避免重复生成订单。
- 订餐约定本身不占用容量；桃子开放匹配餐次时，系统默认带入所有匹配的顾客和自家约定，经桃子确认后生成相应订单。
- 开放确认时，桃子可以调整任一订餐约定在本餐次将生成的订单份数；该调整只影响本餐次，不改变约定中的默认份数。
- 桃子可以跳过本餐次的某条匹配约定，但需要二次确认，并提醒其自行联系顾客。
- 单个餐次订单的修改或取消不改变订餐约定；修改、暂停或结束约定只影响尚未生成的未来订单。
- 桃子可以另外维护一条自家订餐约定；它不需要顾客或配送地址，匹配餐次时生成自家订单。
- 开放餐次时，桃子可以调整本餐次由自家订餐约定生成的份数，不改变之后餐次的默认自家份数。

### 7.7 今日经营与配送

- 桃子可以按餐次查看有效订单数和总份数。
- 自家订单由自家订餐约定生成并计入制作总份数，但不进入配送和收款流程。
- P0 不记录逐单打包进度，也不设置“已打包”状态；制作阶段以餐次总份数为准。
- 桃子点击“开始配送”后，餐次进入陆续配送状态，并可生成微信群通知文案。
- 配送清单按小区、楼栋分组，同小区同楼栋的订单放在一起。
- 桃子可以逐单或按组标记已送达。
- 系统展示配送进度；全部需配送订单送达后，餐次完成。
- 顾客端不展示配送路线或预计送达时间。

### 7.8 线下收款与对账

- 顾客仍通过微信红包或转账向桃子付款；系统不收取、保管或结算资金，也无法自动获知私下付款结果。
- 订单摘要包含顾客称呼、日期、午餐／晚餐、份数和订单编号，不包含详细门牌地址。
- 桃子在微信确认到账后，可按订单编号、顾客称呼、商家私有备注或餐次找到订单，并手工标记“未确认收款／已确认收款”。
- 一笔订单的收款状态覆盖该订单的全部份数，不支持部分份数确认收款。
- 不同餐次的订单分别记录收款状态。
- 桃子可以选择一笔或多笔订单批量标记收款状态，以处理一次微信转账覆盖多个餐次的情况。
- 历史未确认收款订单按餐次归组查找。
- 自家订单和已取消订单不进入未确认收款列表。
- 系统不记录实际转账金额、时间、流水或截图，不统计应收、实收、未收金额和营业收入。
- 未确认收款不自动取消订单或阻止履约；取消订单也不自动触发退款或修改收款记录。

### 7.9 餐次变更通知

- 已有订单后更换菜单，需要确认并通知受影响顾客。
- 已有订单后取消餐次，需要取消关联有效订单并通知顾客。
- 已有订单后不允许修改该餐次价格。
- 提前停止接单不影响已有订单。

## 8. 核心业务规则

1. 周菜单与餐次开放相互独立：有菜单不等于可下单。
2. 顾客只能对已经明确开放预订的餐次自助下单；系统不硬性限制桃子可以开放的未来日期。
3. “待安排”“不供餐”和“已取消”含义不同：待安排尚未决定，不供餐从未开放，已取消则曾经开放但不再履约。
4. 每个餐次的制作份数等于全部有效订单份数之和。
5. 餐次容量是顾客自助下单的限制，不是桃子端的硬上限；桃子可以开放已满或超容量餐次，也可以越过容量手动加单。
6. 截止前，顾客可以修改或取消自己在顾客端创建的订单；截止后需联系桃子处理。桃子代下或订餐约定生成的订单均由桃子维护。
7. 首单申请不是订单，不进入制作份数、配送清单或收款记录；桃子接受后才生成订单。
8. 订单是否有效、是否履约和是否由桃子确认收款是相互独立的维度。
9. 收款记录属于整笔订单，不拆分到订单中的单份套餐。
10. 顾客地址簿属于顾客，订单地址是该笔订单的履约快照。
11. 配送以餐次为批次开始，以单笔订单是否送达记录进度。
12. 菜单生成只使用启用餐品；第一版固定保证每餐 2 荤、2 素、1 汤。
13. 同一顾客在同一餐次至多有一笔有效订单；追加需求修改原订单，订单创建来源保持不变，并记录桃子的调整。

## 9. 核心流程

### 9.1 桃子排菜单并开放餐次

维护菜品池 → 生成周菜单 → 调整并确认 → 在餐次日历中安排供餐状态 → 选择餐次并检查菜单、价格、容量与截止规则 → 确认准确日期和餐别 → 开放并分享。

### 9.2 顾客下单

首次顾客：打开桃子的微信分享 → 查看餐次并授权登录 → 选择份数和地址 → 提交首单申请 → 将申请卡片私聊给桃子 → 桃子确认顾客关系并接受 → 生成订单 → 回到微信付款。

已确认顾客：从分享或小程序首页进入桃子 → 查看餐次 → 选择份数和地址 → 提交并生成订单 → 复制或分享订单摘要 → 回到微信付款。

### 9.3 桃子履约

查看餐次订单与总份数 → 完成备餐 → 开始配送并通知 → 按地址分组查看待配送订单 → 标记送达 → 完成餐次。

### 9.4 桃子核对线下收款

在微信确认顾客实际付款 → 按订单编号或顾客查找订单 → 手工标记已确认收款；一次付款覆盖多笔订单时批量标记。该流程可在备餐、配送前后独立进行，不阻塞订单履约。

## 10. 第一阶段验证指标

- 桃子规划一周菜单所需时间是否明显减少。
- 微信群、私聊和订餐约定是否能够完整进入系统，是否仍发生漏单。
- 桃子是否能只依赖小程序完成备餐份数确认和配送核对。
- 未送达和未确认收款订单是否能够被快速发现。
- 顾客是否能通过微信分享独立完成下单和地址选择。
- 首次顾客能否理解“首单申请尚未预订成功”，桃子能否顺利完成一次确认并建立长期顾客关系。
- 桃子实际使用中最频繁的入口和操作分别是什么。

## 11. 后续扩展方向

- 自定义套餐组成和更多餐品类型。
- 更多排菜属性与规则。
- 小程序内语音录入。
- 在线支付与完整交易闭环：桃子完成经营主体及食品资质准入后，优先采用桃子自己的商户号，或由 Kith Inn 作为服务商／平台将桃子进件为特约商户、二级商户，使货款由微信支付直接结算给桃子；不采用 Kith Inn 公司先收再转的模式。详细调研见 `research/wechat-payment-feasibility.md`。
- 多商家能力及其他社区服务类型。
- 更丰富的经营分析和备餐辅助。
