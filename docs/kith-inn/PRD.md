# 街坊味（Kith Inn）产品需求文档

版本：v0.5 · 更新时间：2026-09-11 · 状态：需求草案，待审阅

本文描述首版的产品目标、使用流程、功能要求和验收结果。尚未确定的边界集中在第 7 节；原型来源、需求确认情况与变更记录见附录。

## 1. 产品背景与目标

桃子为自家做饭，也向周边邻居供餐。她需要提前想好一周做什么，再按实际安排公布午晚餐菜单、记录邻居订餐、汇总制作份数，并核对配送和微信收款。

街坊味最核心的任务是**帮助桃子安排周菜单**：从她会做的菜中生成一周安排，让她通过换菜和逐餐去汤，得到愿意照着做的菜单。产品同时承接后续订餐、制作、配送和对账，减少反复翻聊天记录、抄菜单和算份数的工作。

首版希望达到三个结果：

- 桃子可以在同一处完成一周菜单的生成、调整、确认和查看。
- 公布的餐次菜单与顾客订餐、制作份数、配送清单保持一致。
- 桃子能找到待核的收款记录和停餐应退款项，顾客能查看自己的订单及退款确认状态。

## 2. 用户与使用场景

首版只有桃子一个经营账号，由她操作菜单、订单、配送及核对记录，暂不提供家人协作账号。顾客可以订餐并访问自己的订单，不能访问其他顾客的订单详情。订单访问必须受到保护，具体识别、访问凭据和登录实现留到技术规格确定，不要求真实姓名或手机号验证。

| 用户 | 使用场景 | 需要完成的任务 |
| --- | --- | --- |
| 桃子 | 提前安排一周午晚餐 | 设置本周结构和供餐餐次，生成菜单并调整到满意 |
| 桃子 | 前一天晚上准备次日午餐，当天中午准备晚餐 | 确定实际菜单，决定是否做汤，发到群里开放报名 |
| 顾客 | 从群里的菜单入口订一餐 | 看菜品、填份数和收餐信息，查看或在允许时间内修改订单 |
| 桃子与顾客 | 顾客仍习惯微信私聊订餐 | 桃子代下并回传订单卡，顾客以后可以自行下单 |
| 顾客与桃子 | 希望连续多天固定订午餐、晚餐或两餐 | 顾客申请，桃子审核，微信付款后由桃子标记生效 |
| 桃子 | 制作、送餐和核对款项 | 看总份数和配送名单，标记送达，核对收款；停餐时处理通知及退款 |

**术语约定：**

| 术语 | 本文含义 |
| --- | --- |
| 餐次 | 某个具体日期的午餐或晚餐；同一天午晚餐分别处理 |
| 周结构 | 桃子为一周设置的一套统一荤、素、汤数量；逐餐去汤不改变周结构 |
| 订单成立 | 普通订餐提交成功并形成有效订单，不要求先付款；连续订餐申请提交不等于生效 |
| 连续订餐生效 | 审核通过、微信付款后，由桃子明确标记生效，才为约定餐次保留份数 |
| 有效份数 | 计入对应餐次供餐统计的份数；顾客订餐包含有效自助单、代下单及已生效连续订餐，制作份数另加自家份数；已取消和未生效的申请不计入 |
| 勾销（划掉） | 同一操作的两种称呼，正文沿用原型的“划掉”；表示截图核对清单中的该项处理完成，可恢复，不表示平台验证了资金到账 |
| 退款确认 | 顾客表示已收到对应退款的记录；待确认只表示确认尚未完成，不说明资金是否到账 |

## 3. 首版范围

首版覆盖完整供餐流程，周菜单是核心功能。各模块的交付结果如下。

| 模块 | 交付结果 | 需求章节 |
| --- | --- | --- |
| 菜品池 | 批量录入菜名、确认荤素汤分类，维护可用菜品 | 5.1 |
| 周菜单 | 安排七天午晚餐，按周统一结构生成，换菜、逐餐去汤、确认和查看 | 5.2 |
| 餐次公布 | 生成群里使用的菜单说明和预订入口，公布后锁定对应餐次 | 5.3 |
| 普通订餐与代下 | 顾客自助下单，桃子代下后分享订单卡，按权限修改或取消 | 5.4 |
| 连续订餐 | 申请、审核、微信付款、生效，以及后续餐次履约 | 5.5 |
| 制作与配送 | 汇总准确份数，按收餐信息配送，记录送达进度 | 5.6 |
| 收款对账 | 微信截图辅助匹配，可手动划掉或恢复核对项，提醒未收款订单 | 5.7 |
| 停餐与退款 | 取消受影响餐次，生成群公告和逐单退款清单，顾客确认收到退款 | 5.8 |

使用场景以微信小程序与微信群、私聊之间的衔接为基础。菜单在群里公布，报名记录在小程序中形成；桃子负责实际发送微信消息。收款和退款在微信中完成，系统提供记录与辅助核对。

首版不包含小程序内支付、商家发现或店铺市场、顾客自选菜品和个性化套餐、菜谱、采购库存、成本营养分析、配送路线规划及预计送达时间。

## 4. 核心使用流程

### 4.1 桃子安排周菜单

| 步骤 | 桃子的操作 | 系统呈现的结果 |
| --- | --- | --- |
| 1. 准备菜品 | 首次粘贴会做的菜，确认分类；以后随时补充或停用 | 一份可用于排菜的菜品池 |
| 2. 设置目标周 | 选择需要安排的一周、需要做饭的午晚餐，以及本周统一荤素汤数量 | 七天的供餐安排和一套周结构 |
| 3. 生成菜单 | 点击生成本周菜单 | 按日期组织的午晚餐草稿 |
| 4. 调整餐次 | 逐日查看，替换不满意的菜，对具体午餐或晚餐去汤或恢复汤 | 仅目标位置发生变化，其他安排保留 |
| 5. 确认周菜单 | 确认调整结果 | 保存菜单，进入只读的本周菜单总览，便于回看 |
| 6. 公布具体餐次 | 从总览继续准备某餐菜单说明和预订入口 | 顾客可查看并报名该餐；公布后的餐次锁定 |

**确认周菜单与公布餐次是两个动作。** 总览用于查看已保存的安排；尚未公布的餐次仍可进入调整流程。真正锁定菜品的节点是对应餐次公布，确认整周菜单不等于一次性公布整周。

### 4.2 普通订餐与日常供餐

> 桃子在群里公布某餐菜单 → 顾客进入小程序提交订单 → 订单成立并汇总份数 → 桃子制作和配送 → 微信收款、截图辅助对账。

顾客通过私聊订餐时，由桃子代录订单并回传订单卡，之后同样进入制作与配送流程。普通订餐可以先送餐后收款；送达后未收到款时，由桃子主动提醒。

### 4.3 连续订餐

> 顾客提交连续订餐申请 → 桃子审核通过 → 顾客微信付款 → 桃子标记生效 → 对应餐次保留份数并进入供餐流程。

未来菜单尚未公布也可申请。待审核和待付款的申请尚未生效；拒接申请时，由桃子向申请人私聊说明。某餐无法供餐时，进入停餐与退款流程，其他餐次继续履约。

## 5. 功能需求与验收

验收编号随对应需求保持稳定，不随章节位置重排。保留原有 AC-01～19，本次新增场景从 AC-20 追加，因此各章节中的编号不一定连续。

### 5.1 菜品录入与维护

**使用场景与入口：** 桃子首次建立菜品池，或从“我的”继续补充菜品。对应[桃子端原型的“菜品池初始化”](https://github.com/code-for-people-2026/ideal/blob/cb71b2e84ac0665a288b1634096438c19b743918/docs/kith-inn/yao/prototype-implementation/prototype-taozi/index.html)。

**操作与结果：**

1. 桃子按每行一道菜粘贴清单，至少输入一道非空菜名。
2. 系统根据菜名建议荤菜、素菜或汤分类，展示待确认清单，暂不写入菜品池。
3. 桃子点击更换图标，按“荤 → 素 → 汤”循环修正分类；菜名有误时可以返回修改。
4. 点击“确认加入菜品池”后保存，并显示加入的菜品数量。之后可逐道新增、改名、改分类、停用或恢复。

菜品录入只保存菜名和分类，不要求主料、配方、口味、忌口或采购信息，也不增加荤菜数量的录入门槛。桃子确认的信息不会被系统无提示覆盖。停用菜品不参与后续生成和换菜；改名或删除不影响历史菜单保留的菜品内容。

**验收 AC-01：** 空清单无法继续；预览内容未确认前不参与排菜；返回改名及循环改分类均可用，确认后只保存菜名和分类。菜品不足以排满菜单时的处理见 Q2。

### 5.2 安排周菜单

**使用场景与入口：** 桃子进入“本周菜单”提前安排。对应[桃子端的周菜单与换菜](https://github.com/code-for-people-2026/ideal/blob/cb71b2e84ac0665a288b1634096438c19b743918/docs/kith-inn/yao/prototype-implementation/prototype-taozi/index.html)，以及[客户体验原型中的“修改菜单”和“本周菜单总览”](https://github.com/code-for-people-2026/ideal/blob/cb71b2e84ac0665a288b1634096438c19b743918/docs/kith-inn/yao/prototype-customer/index.html)。

**周安排与生成：**

- 一周覆盖七天，每天午餐、晚餐分别安排，不做的餐次可以跳过。
- 一周采用一套统一的荤、素、汤数量。例如本周两荤一素一汤，下周可以三荤一素一汤；具体数量由桃子设置。
- 系统从菜品池中可用的同类菜品生成各餐菜单，同一餐不重复放入同一道菜。
- 同一道菜尽量整周不重复；不足以覆盖整周时，允许跨餐重复并尽量隔开。
- 生成结果按日期组织，同一天午晚餐放在一起，桃子可以逐日浏览。

**换菜与逐餐去汤：**

- 桃子可以随机“换一道”，也可以从同类候选中手选。每次只替换目标菜，保留其他菜和其他餐次。
- 候选须满足类型一致、处于可用状态、与本餐其他菜不重复；没有其他可用候选时明确提示。
- 公布前，桃子可以移除或恢复某个餐次的汤，午餐和晚餐分别操作。荤菜和素菜数量仍遵守本周结构。
- 去汤不改变本周统一结构，不重新排列其他菜，也不自动改变每份价格。

**保存与确认：** 调整结果可以保存。确认后展示只读的周菜单总览，再按餐次生成预订内容；应用重开或换设备后仍可读取已保存菜单。公布前可调整对应餐次，公布后换菜、去汤、重新生成或修改周设置都不能改动该餐菜单。

**验收：**

| 编号 | 场景与预期结果 |
| --- | --- |
| AC-02 | 本周两荤一素一汤，下周三荤一素一汤，各周按自己的统一结构生成；跳过的餐次不安排菜单 |
| AC-03 | 周二晚上调整周三午餐和周五晚餐：分别去汤后，仅这两餐不含汤；两餐其他菜、其他餐次及周结构保持原样，公布前可以恢复 |
| AC-04 | 菜品足以填满一餐但不足以整周不重复时，允许跨餐重用并尽量隔开，同餐仍不重复使用同一道菜 |
| AC-05 | 换一道菜并确认周菜单后，总览显示调整结果；再次进入仍能读取，其他位置未变化；确认周菜单不会自动公布所有餐次 |

常用周安排的继承和已有菜单遇到周结构变化的处理见 Q1；生成缺口、手选入口及候选轮换细节见 Q2。

### 5.3 确认餐次与群里公布

**使用场景与入口：** 桃子从周菜单继续准备某餐预订内容。对应[桃子端“确认与分享”](https://github.com/code-for-people-2026/ideal/blob/cb71b2e84ac0665a288b1634096438c19b743918/docs/kith-inn/yao/prototype-implementation/prototype-taozi/index.html)。

桃子通常在前一天晚上准备次日午餐说明，当天中午准备晚餐说明。公布前核对实际菜品、是否做汤和订餐信息，生成用于群里的说明及小程序预订入口，再主动发送。

餐次须清楚展示日期、午餐或晚餐、完整菜品、每份价格、截止时间及剩余份数。桃子的每份价格固定，不随去汤或换菜自动变化。顾客从入口进入对应餐次，查看菜单并报名。

周菜单属于桃子的内部计划，具体餐次公布后才开放普通订餐。公布后该餐菜单锁定；无法按原菜单供餐时，取消餐次并通知顾客，按 5.8 处理。停止接单只关闭新订单入口，不等于取消已有订单。

**验收：**

| 编号 | 场景与预期结果 |
| --- | --- |
| AC-10 | 桃子发群后，顾客从对应餐次入口在小程序报名，形成订单；系统无需读取微信接龙结果 |
| AC-11 | 公布后尝试换菜、去汤、重新生成或修改周结构，对应餐次菜单始终保持锁定；不能供餐时进入取消和通知流程 |

实际发群、开放报名与锁定的操作衔接，以及提前处理未来餐次的允许范围见 Q3。当前经营习惯不作为禁止提前处理其他日期的硬限制。

### 5.4 普通订餐、代下与订单修改

**使用场景与入口：** 顾客从群内预订入口进入，桃子从订单列表手动补单。对应[顾客端普通订餐与“我的订单”](https://github.com/code-for-people-2026/ideal/blob/cb71b2e84ac0665a288b1634096438c19b743918/docs/kith-inn/yao/prototype-implementation/prototype-customer/index.html)，以及[客户体验原型的私聊代下、订单卡场景](https://github.com/code-for-people-2026/ideal/blob/cb71b2e84ac0665a288b1634096438c19b743918/docs/kith-inn/yao/prototype-customer/index.html)。

顾客查看餐次菜单，填写份数和收餐信息后提交。已开放、未截止且有余量时，订单直接成立，首次下单同样适用。桃子代下时记录顾客、日期、餐次、份数及收餐信息，再回传订单卡，引导顾客以后自行下单。

**代下订单归属：** 顾客发起与本人订单的关联，由桃子确认一次，确认后才能查看对应订单详情。未经桃子确认，收到或转发订单卡均不能获得订单详情访问权；不能仅凭称呼相同或手机号相同自动关联。此确认只用于代下订单归属，不增加普通自助下单的审核步骤。重复顾客记录等剩余边界见 Q5。

午餐和晚餐分别归属具体餐次。同一顾客同一餐次至多有一笔有效订单，追加份数修改原订单；普通顾客下单不能超过余量，重复提交不能生成重复有效订单。

**修改权限：**

| 订单或操作 | 顾客可以做什么 |
| --- | --- |
| 顾客自己直接下的单餐，尚未截止 | 可以修改或取消；增加份数仍受余量限制 |
| 桃子代下的单餐 | 联系桃子修改或取消，关联本人后也不开放自助修改 |
| 连续订餐及其对应餐次 | 联系桃子调整或停止，不能自行批量停止剩余餐次 |
| 已截止的单餐 | 联系桃子处理 |

桃子修改过顾客自助订单后，订单仍保留原创建来源。取消后订单退出有效份数和待配送清单，并释放占用份数。已送达或已记录收款的更正权限见 Q6。

收餐信息只要求桃子能辨认的称呼和完成配送所需的收餐位置，手机号选填，不要求真实姓名或手机号验证。普通订餐、桃子代下和连续订餐遵守同一信息要求；小区、楼栋等位置字段如何组织见 Q6。顾客修改地址簿不会自动改写既有订单已确认的地址。

**验收：**

| 编号 | 场景与预期结果 |
| --- | --- |
| AC-06 | 首次顾客在未截止且有余量的已公布餐次提交订单，直接预订成功，无首单审核或先付款要求 |
| AC-07 | 桃子首次代下并发订单卡后，顾客发起关联，经桃子确认一次后能查看自己的记录并在以后自行下单；不得错误归属其他顾客 |
| AC-09 | 自助单在截止前可自行修改或取消；代下单、连续订餐和截止后的订单引导联系桃子；操作遵守上表权限 |
| AC-15 | 重复提交不产生重复有效订单；多名顾客同时订最后余量时，普通下单不超容量 |
| AC-20 | 已填写可辨认称呼和必要收餐位置，手机号留空时仍可提交普通订单或连续订餐申请，桃子也可代下；不要求真实姓名或手机号验证，普通单直接成立，连续订餐仍按审核、付款、标记生效的流程处理 |
| AC-21 | 顾客发起代下订单关联后、桃子确认前无法查看该单详情，订单卡转发给其他人也不授予详情访问权；桃子确认后仅关联本人可从顾客端访问该单，修改权限仍按上表执行 |

### 5.5 连续订餐

**使用场景与入口：** 顾客选择连续多天订餐，桃子从订单列表审核。对应[顾客端“长期订单”](https://github.com/code-for-people-2026/ideal/blob/cb71b2e84ac0665a288b1634096438c19b743918/docs/kith-inn/yao/prototype-implementation/prototype-customer/index.html)和[桃子端长期订单卡](https://github.com/code-for-people-2026/ideal/blob/cb71b2e84ac0665a288b1634096438c19b743918/docs/kith-inn/yao/prototype-implementation/prototype-taozi/index.html)。本文将原型中的“长期订单”统一称为连续订餐。

**申请内容：**

| 内容 | 要求 |
| --- | --- |
| 开始日期、连续天数 | 有明确起止范围；连续天数为 4—90 的整数，开始日期可选范围见 Q4 |
| 每天餐次 | 午餐、晚餐或两餐，至少选择一餐 |
| 每餐份数 | 所选餐次分别填写 1—20 的整数份数 |
| 配送地址 | 展示并确认实际收餐地址 |
| 金额摘要 | 固定每份价格 × 每天所选餐次份数合计 × 连续天数，提交前展示分餐计算及预估合计 |

**审核与生效：**

| 状态 | 桃子或顾客的操作 | 结果 |
| --- | --- | --- |
| 待审核 | 桃子同意申请 | 进入待付款，尚未生效 |
| 待审核 | 桃子填写简短说明并拒接 | 显示已拒接，可复制私聊文案发给申请人，群里不公开审核结果或原因 |
| 待付款 | 顾客微信付款，桃子确认后点击“标记已收到微信付款” | 进入生效中，按约定日期和餐次保留份数 |
| 生效中 | 桃子按已公布的各餐菜单供餐 | 对应份数纳入制作配送；到期不自动续订 |

桃子也可以代建连续订餐，仍须确认微信付款并标记生效。审核通过、对账截图划掉和菜单公布都不会自动使连续订餐生效；尚未生效的申请不计入有效供餐份数。

未来菜品及是否有汤可在申请后随餐次公布确定。顾客能查看申请处理结果、生效订餐、已公布菜品和停餐退款。修改或停止剩余餐次由桃子处理，受影响份数须同步退出制作配送清单；已付款部分按 5.8 记录退款。

**验收：**

| 编号 | 场景与预期结果 |
| --- | --- |
| AC-08 | 审核通过后显示待付款；桃子确认微信付款并标记后才生效。之后菜单公布不重复计入份数，截图划掉也不自动生效 |
| AC-18 | 天数不在 4—90 整数范围、未选任何餐次或所选餐次份数不在 1—20 整数范围时无法提交；提交前可核对份数、地址和金额 |
| AC-19 | 拒接后显示处理结果和可复制的私聊说明，不计入生效份数，不自动在群里公开 |

开始日期、不供餐日期、重复订单、容量冲突和剩余餐次调整见 Q4。各餐记录的形成方式由后续规格确定，需保证生效份数不漏算、不重复。

### 5.6 制作份数与配送

**使用场景与入口：** 桃子按餐次查看订单汇总和配送清单。对应[客户体验原型的经营汇总](https://github.com/code-for-people-2026/ideal/blob/cb71b2e84ac0665a288b1634096438c19b743918/docs/kith-inn/yao/prototype-customer/index.html)，配送细节参考[配套用户故事](https://github.com/code-for-people-2026/ideal/blob/cb71b2e84ac0665a288b1634096438c19b743918/docs/kith-inn/yao/user-stories.md)。

制作份数按餐次汇总：顾客自助、桃子代下、已生效连续订餐，以及自家用餐份数。自家份数只计制作，不进入顾客配送和收款清单；待审核、待付款、已拒接及已取消的订餐不计入供餐份数。

顾客可订余量为餐次容量减去有效顾客订餐份数，最低显示为 0。已生效连续订餐的保留份数计入对应餐次，菜单公布时不重复扣减；尚未生效的申请不占用有效订餐份数。

配送清单按小区、楼栋组织，包含订单份数及已确认的收餐信息。桃子可以逐单或按组标记送达，查看待配送、配送中和已送达的进度；所有需配送订单送达后，该餐次配送完成。送达不自动标记收款，普通订单未付款也不阻止配送完成。

**验收 AC-13：** 自助、代下和生效连续订餐各计一次，自家份数计制作、不计配送；取消或停止的餐次份数退出清单。逐单或按组标记送达后进度一致，已送达记录可查。

容量和截止设置、自家份数的录入方式、配送分组，以及顾客未留手机号且微信联系不上时的配送处理见 Q6；连续订餐的容量冲突处理见 Q4。

### 5.7 微信收款与截图辅助对账

**使用场景与入口：** 桃子从订单列表进入收款对账。对应[桃子端“收款对账”和“对账清单”](https://github.com/code-for-people-2026/ideal/blob/cb71b2e84ac0665a288b1634096438c19b743918/docs/kith-inn/yao/prototype-implementation/prototype-taozi/index.html)，付款提醒参考[客户体验原型的送餐后私聊](https://github.com/code-for-people-2026/ideal/blob/cb71b2e84ac0665a288b1634096438c19b743918/docs/kith-inn/yao/prototype-customer/index.html)。

桃子可以一次选择多张微信收款截图。系统读取姓名、金额和时间，每张截图形成一项清单记录，并与订单做候选匹配。

| 匹配结果 | 系统行为 | 桃子可以做什么 |
| --- | --- | --- |
| 顾客、金额、日期等信息能唯一匹配订单 | 自动划掉该项，显示对应订单及明确依据 | 核对依据，必要时恢复待核 |
| 存在多个候选 | 保留待核，说明歧义 | 手动划掉，无须填写理由 |
| 找不到匹配订单 | 保留待核，说明无匹配 | 手动划掉，无须填写理由 |
| 截图完全识别失败，未读出姓名、金额和时间 | 明确显示识别失败，保留原截图和待核项 | 查看原截图并人工核对后划掉，或重新识别；无须补录字段或填写理由 |

清单显示处理进度，区分系统和手动划掉；已划掉项都可恢复并重新核对。勾销代表该项处理完成，不代表平台验证了微信资金到账；无明确匹配时，不因手动划掉截图而擅自关联订单。连续订餐仍由桃子单独确认付款并标记生效。

普通订单送达后尚未收到款时，桃子可以主动发送付款提醒；提醒发出不会自动记录为已收款。

**验收：**

| 编号 | 场景与预期结果 |
| --- | --- |
| AC-14 | 普通订单送达但未付款，配送仍可完成，桃子可以主动提醒；微信收款后可用截图核对 |
| AC-16 | 唯一匹配项由系统划掉并保留依据，多候选或无匹配项待桃子处理；手动划掉不要求理由，所有已划掉项可恢复且来源可区分 |
| AC-22 | 截图未能识别出姓名、金额和时间时明确显示失败，原截图仍可查看；桃子可以重新识别，也可人工核对后直接划掉，无须补录字段或填写理由；划掉后显示手动来源且可恢复，不自动关联订单或使连续订餐生效 |

### 5.8 停餐与退款

**使用场景与入口：** 桃子无法履行某餐供餐安排时取消对应餐次。对应[桃子端停餐确认与退款清单](https://github.com/code-for-people-2026/ideal/blob/cb71b2e84ac0665a288b1634096438c19b743918/docs/kith-inn/yao/prototype-implementation/prototype-taozi/index.html)，以及[顾客端“我的订单”退款确认](https://github.com/code-for-people-2026/ideal/blob/cb71b2e84ac0665a288b1634096438c19b743918/docs/kith-inn/yao/prototype-implementation/prototype-customer/index.html)。

1. 停餐确认前，展示受影响顾客、餐次、份数，以及已付款部分的预计应退金额。
2. 桃子确认后，关闭受影响餐次的普通订餐入口，取消对应履约安排，并从制作和配送清单中移除受影响份数。
3. 系统生成微信群公告和逐单退款清单。桃子复制公告后主动发群，系统不自动私聊所有顾客。
4. 已付款部分按取消餐次份数 × 该订单每份价格计算应退金额；未付款订单取消不生成退款任务。连续订餐只退受影响餐次，其他餐次继续生效。
5. 桃子在微信逐笔退款。顾客查看停餐原因和应退金额，收到后点击“确认已收到退款”，状态从待确认退款变为已确认收到。

桃子端列出待微信退款项，顾客端记录收到退款的确认。系统保存停餐原因、应退金额及顾客确认，不代为退款或验证资金到账。

**退款确认更正：** 已付款连续订餐因停餐产生退款，顾客误点“确认已收到退款”时，联系桃子更正；桃子将对应记录恢复为待确认退款，并保留原确认及本次更正记录。顾客未确认只表示确认尚未完成，不据此判断微信资金是否到账，也不影响其他餐次继续履约。更正确认状态不再次发起退款，普通未付款订单取消仍不产生退款项。

**验收：**

| 编号 | 场景与预期结果 |
| --- | --- |
| AC-12 | 停餐前可核对受影响份数和预计退款；确认后关闭对应入口、移除制作配送份数并生成公告和已付款退款清单，其他连续餐次继续生效 |
| AC-17 | 顾客可核对该餐应退金额并确认收到，确认后状态更新；未付款取消无退款项，停一餐不退整段连续订餐 |
| AC-23 | 已付款连续订餐停餐退款后，顾客误点收到并联系桃子，桃子可恢复待确认退款；原确认和更正记录均保留，顾客实际收到后可再次确认；待确认不被当作资金未到账的证明，不影响其他餐次，也不重复产生退款任务 |

### 5.9 信息保护与记录恢复

收集的信息仅用于订餐、履约和必要核对，称呼、收餐位置及选填手机号遵守 5.4 的要求。顾客只能访问自己的订单；原截图及经营核对记录由桃子处理，不能通过转发订单卡绕过访问保护。

已保存的菜单、订单和核对记录需要具备恢复能力，并须落实项目公开的数据退出和删除承诺。具体安排及确定阶段见 7.2，承诺出处见附录 A。

## 6. 验收与效果判断

每个功能按第 5 节的验收场景检查。首次完整验证应串起三条路径：桃子安排一周菜单并公布一餐、顾客自助或桃子代下后完成制作配送与对账、连续订餐生效后发生一次停餐退款。涉及未定边界的场景，先补齐第 7 节对应问题再完成验收。

真实试用以“确认后的周菜单可直接用于供餐，无需另抄”为核心目标，并观察以下结果。先记录现状和试用结果，再确定量化改进目标；目前不预设分钟数或成功率。

| 目标 | 观察方式 |
| --- | --- |
| 确认后的周菜单可直接用于供餐，无需另抄 | 请桃子按保存的周菜单准备实际供餐，记录是否仍需另抄及原因，同时记录生成到确认所需时间和调整情况 |
| 订餐与履约记录可信 | 核对订单、制作份数和配送名单是否一致，是否仍有漏单或重复计数 |
| 对账与退款容易跟进 | 检查未收款订单、截图待核项、应退金额和顾客确认能否清楚找到 |
