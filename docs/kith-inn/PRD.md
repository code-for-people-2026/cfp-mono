# 街坊味（Kith Inn）产品需求文档

版本：v0.11 · 更新时间：2026-09-21 · 状态：核心闭环已可本地试用，按用户纠正的排好菜工程原型校正主流程，待验收

首版范围已重新确定为：**桃子排好一周菜单，调整、保存，并把菜单内容分享到微信。订餐继续沿用微信。** 本版替代 v0.5 的“首版覆盖完整供餐流程”安排；用户故事见 [USER-STORIES.md](USER-STORIES.md)，技术方案见 [TECH-SPEC.md](TECH-SPEC.md)，开发细节见 [功能规格](../../specs/022-kith-inn-menu-mvp/spec.md)。2026-09-20 用户选择 1A、2A、3A，三个业务边界已确认；决策记录见第 7 节。

## 1. 产品背景与目标

桃子为自家做饭，也向周边邻居供餐。安排一周吃什么、反复换菜和整理发群内容，是本次优先解决的问题。

第一版帮助桃子从会做的菜中生成一周午晚餐安排，按实际情况换菜、去汤，保存成可以照着做的菜单，再把某一餐的菜单内容发到微信群。顾客仍通过现有微信方式订餐；桃子继续在微信中处理订餐、份数、送餐和款项。

首版只验证三个结果：

- 能从菜品池生成符合本周安排的菜单，并调整到愿意照着做。
- 保存后能再次找到同一份菜单，重开应用或换设备也不会丢失。
- 发群时可以直接使用工具生成的菜单文字，不必重新抄菜名。

## 2. 用户与术语

产品内只有桃子一个经营账号，暂不提供家人协作账号。邻居是微信菜单的接收者，第一版不需要在本产品注册、登录、下单或查看订单。桃子的账号识别和恢复方式由技术规格确定，不以开发一个顾客账号系统作为前置条件。

| 术语 | 本版含义 |
| --- | --- |
| 菜品池 | 桃子会做且可用于排菜的菜名及荤、素、汤分类 |
| 餐次 | 某个具体日期的午餐或晚餐；同一天午晚餐分别安排 |
| 周结构 | 一周统一使用的荤、素、汤数量；不同周可以不同，逐餐去汤不改变它 |
| 确认周菜单 | 保存当前安排并进入只读总览，方便回看；不表示已发到微信 |
| 菜单分享 | 从已保存的指定餐次生成菜单文字，由桃子复制并主动发到微信；不产生系统订单 |

旧版的订单成立、连续订餐生效、有效份数、勾销和退款确认不再作为首版业务概念；其历史定义见附录中的固定版本。

## 4. 核心使用流程

| 步骤 | 桃子的操作 | 系统结果 |
| --- | --- | --- |
| 1. 准备菜品 | 粘贴会做的菜，核对荤素汤分类后保存 | 可用于排菜的菜品池 |
| 2. 设置一周 | 选择目标周、需要做的午晚餐及本周统一结构 | 一周的排菜条件 |
| 3. 生成与调整 | 生成菜单，换掉不满意的菜 | 按日期组织的午晚餐安排 |
| 4. 保存与确认 | 保存结果，确认后查看周总览 | 再次打开时可回看的菜单 |
| 5. 分享某餐 | 选择一餐，核对并复制菜单文字，切到微信发送 | 可直接使用的菜单内容；实际发送由桃子完成 |
| 6. 日常使用 | 回看菜单准备做饭，继续用微信处理邻居订餐 | 用实际使用验证排菜是否省事 |

确认周菜单、生成文字、复制文字和实际发群是不同动作。系统不因生成或复制成功而声称微信群已收到消息，也不因此开放订餐。确认、复制或实际发群后均可再次编辑。生成后修改周结构须先确认会覆盖已有调整；已发微信文字不会自动更新，由桃子自行通知邻居。首版不设置公布锁或解锁动作。

## 5. 功能需求

### 5.1 菜品录入与维护

1. 桃子按每行一道菜粘贴清单，至少输入一道非空菜名。
2. 系统建议荤菜、素菜或汤分类，展示待确认清单，确认前不写入菜品池。
3. 桃子点击更换图标，按“荤 → 素 → 汤”循环修正分类；菜名有误时可以返回修改。
4. 点击“确认加入菜品池”后保存并显示加入数量；以后可以逐道新增、改名、改分类、停用或恢复。

菜品只保存菜名和分类，不要求主料、配方、口味、忌口或采购信息，不增加荤菜数量的录入门槛。建议分类须经桃子确认，不能无提示覆盖她的修改。首版采用简单菜名关键词建议，不确定时仍可人工改分类；不依赖AI服务或要求填写主料。重复菜名明确提示，整批不入池，修改后再确认；已停用同名菜可在维护中恢复。

停用菜品不参与后续生成和换菜。菜品改名或停用不能反向改写已保存菜单中的菜名；历史展示内容需要保留。某类可用菜不足以排满一餐时，提示缺少哪类及所需、现有数量，先补菜或调整周结构，再生成；不返回带空位的菜单。

### 5.2 安排、调整与保存周菜单

**周安排与生成：**

- 一周覆盖七天，每天午餐、晚餐分别安排，不做的餐次可以跳过。
- 一周采用一套统一荤、素、汤数量。例如本周两荤一素一汤，下周三荤一素一汤；具体数量由桃子设置。
- 系统从可用的同类菜品中生成各餐菜单，同一餐不重复放入同一道菜。
- 同一道菜尽量整周不重复；不足以覆盖整周时允许跨餐重复，并尽量隔开。
- 本周入口和编辑页按排好菜工程原型区分。编辑表格在手机同时展示两天，横向查看七天，午晚餐分组，支持“荤菜／全部”切换；选中区右侧纵排“换一道／自己选”，单餐做汤安排与周设置由本周入口进入。横向拖动或滚动结束后按日期列对齐，包含周末边界；编辑、检查及历史共用此行为，不停在裁切半列的位置。
- 已生成后可以修改本周结构。重新生成前明确提醒会覆盖之前的换菜、逐餐去汤等整周调整；桃子确认后才重排。取消或生成失败保留原编辑内容和已保存菜单；生成成功后仍需检查并保存，才覆盖服务器上的旧菜单。
- 任一需要的分类不足以填满一餐时，整次生成失败并列明所需和可用数量；不生成部分菜单。足以填满一餐但不足以整周不重复时，仍允许跨餐重用。

**定点换菜与逐餐去汤：**

- “换一道”进入独立候选页，随机建议合法候选；“自己选”进入可搜索的同类菜选择状态。确认替换才改变目标位置，返回或取消保留原内容，不改变其他菜和餐次。
- 候选须满足分类一致、处于可用状态、与本餐其他菜不重复；没有其他候选时明确提示。
- 可以决定某个餐次做汤或不做汤，午餐和晚餐分别操作；荤菜和素菜数量仍遵守本周结构。供餐决定放在已保存菜单的具体餐次界面，以“本餐做汤／本餐不做汤”表达；整周修改菜单页只换菜，不提供去汤／恢复按钮。
- 去汤不改变周结构，不重新排列其他菜。首版不计算订单金额，也不因去汤推导价格变化。
- 实际做饭时临时不做汤：从已保存周的本周入口直接选择日期和午／晚餐，去掉或恢复这餐的汤，再显式保存本餐调整；不必进入整周编辑或再次确认整周。入口明确目标餐，默认所选周内今天的已安排餐，否则默认该周首个已安排餐。只有已保存菜单可开始此流程；存在未保存的整周或设置调整时先按已有方式处理，不夹带或丢弃草稿。跳过餐和本周汤数量为零时不提供去汤动作。
- 单餐保存属于普通编辑保存，清除原确认状态，不自动确认整周。去汤只改变目标餐的汤状态；恢复仍按原汤可用性规则处理。取消不写入，失败不显示成功；成功后重开、回看及重新生成该餐分享文字均采用新内容。

**保存与回看：** 完整的调整结果可以保存，不接受菜位缺失的菜单。按工程原型先进入只读横向表检查，进入检查页不写入，返回保留草稿；最终“保存本周菜单”一次原子保存并确认当前内容，成功才显示已保存并提供文字复制。确认本身不代表发送给邻居，确认或分享后均可继续编辑；进入编辑、取消编辑不改已保存内容。普通保存后需重新确认。历史保持自己的入口，直接显示已保存周的同款只读表并左右切换保存周；重新进入、重开应用或换设备仍能读取已保存内容。保存失败须明确提示，不能显示为已保存或覆盖原来的完整记录。

本次实施默认新周独立设置，不自动复制上周；换菜提供随机与手选两个入口，不增加跨次候选轮换记录。恢复汤时先使用可用原汤，失效项须重新选齐后一起恢复；取消或汤不足则维持去汤，不改其他菜。以上默认约定可在评审中调整，详见功能规格第2.2节。生成后重排、缺菜失败与分享后编辑按已确认的 Q1～Q3 执行；“确认周菜单”不是不可再改的发布动作。

### 5.3 菜单文字分享

桃子从周总览选择一个已保存的餐次，系统生成包含**完整年份日期、午餐或晚餐、完整菜品名称**的文字。去掉汤的餐次不列出汤；文字必须与所选餐次的已保存内容一致。若页面仍有未保存修改，应先保存或明确放弃修改再生成文字，不自动丢弃草稿，也不把尚未保存的内容伪装成最终菜单。

桃子核对文字后复制，主动切换到微信群或私聊发送。复制成功只说明文字已复制；复制失败需提示并允许重试，不修改已保存菜单。首版不读取群消息，不自动发群，不导入接龙，也不生成订单。

生成文字前重新读取已保存菜单，读取失败则提示重试；文字取自本次读取的保存内容；随后修改菜单不会自动改写已复制、已发送的文字。临时变更或不做某餐时，桃子仍需在微信中通知相关邻居。

**分享后的修改：** 允许继续编辑、保存并重新生成文字复制。根据2026-09-21用户反馈，编辑页及复制页不再展示旧微信消息或通知邻居的解释性提示；消息本身不会随菜单修改而更新，由桃子自行通知邻居。系统不判断消息是否已发出，不增加“已公布”记录、锁定或解锁操作。首版默认文字不带价格，桃子可在微信自行补充；不新增固定单价、容量、截止时间或剩余份数管理。

### 5.4 访问保护、保存与恢复

菜品池、内部周菜单及其修改能力只对桃子的经营账号开放，不能仅靠隐藏按钮保护。分享到微信的菜单文字只包含桃子选择对外提供的内容，不携带内部管理入口或访问凭据。

首版不收集顾客称呼、手机号、地址、订单或收款截图。账号关联信息和保存的菜单仅用于当前产品功能、访问保护及必要恢复。已保存记录需要具备恢复能力；恢复安排、数据保留期限、用户退出和删除流程须在上线前明确并验证。项目公开的数据退出承诺及出处见附录 A。

## 6. 验收与试用目标

编号跟随原需求保留，不因缩小范围重新编号。首版沿用 AC-01～05，新增菜单分享 AC-24 和基础保障 AC-25；原 AC-06～23 移入历史范围，具体对应关系见附录 B。

| 编号 | 场景与预期结果 |
| --- | --- |
| AC-01 | 空清单不能提交；建议分类可循环修正，菜名可返回修改；预览未确认前不参与排菜，确认后只保存菜名和分类；停用不参与新排菜，维护菜品不覆盖历史菜单 |
| AC-02 | 本周两荤一素一汤、下周三荤一素一汤，各周遵守自己的统一结构；跳过餐不生成，按日期组织午晚餐；已有菜单改结构时先提醒会覆盖换菜和去汤调整，确认才重生成，取消或失败保留原结果，成功预览仍需保存 |
| AC-03 | 菜单已经保存，到了周三午餐实际做饭时临时不做汤；从本周入口直接选择该餐，设为“本餐不做汤”并保存，无需整周编辑／确认。仅这餐不含汤，其他菜、其他餐次和周结构不变；重新打开与复制该餐文字均无汤，可恢复并保存。取消不写入，失败保留调整且不显示成功。整周编辑页不提供去汤／恢复按钮；提前删掉未来餐汤的测试不能代替本场景 |
| AC-04 | 足以填满一餐但不足以整周不重复时，允许跨餐重用并尽量隔开，同餐仍不重复；需要两道荤菜却只有一道时，提示所需和现有数量，整次不生成，补菜或改结构后可重试；不生成或保存缺位菜单 |
| AC-05 | 随机或手选换掉指定菜，其他位置不变；保存确认后总览显示结果，重开及换设备后仍可读取；确认后可继续编辑，进入或取消不改保存记录，普通保存清除原确认状态，可再次保存并确认；失败不显示成功，不破坏已保存菜单 |
| AC-24 | 从已保存餐次生成的文字含完整日期、午晚餐和菜名，去汤结果一致；复制不冒充发送，不产生订单；失败可重试且不改菜单；复制或发群后可编辑保存并重新复制，由桃子自行通知邻居，旧文字不自动更新，无公布锁或解锁 |
| AC-25 | 未获桃子经营权限的请求不能读取或修改内部菜品和菜单；分享文字不含访问凭据；按已确定的恢复安排验证可找回保存记录，并完成退出删除流程验证 |

联合验收主路径：**建立菜品池 → 生成一周菜单 → 定点换菜 → 保存确认 → 做饭时调整某餐是否做汤并保存 → 重开回看 → 分享指定餐次文字**。Q1～Q3 按已确认规则验收；上线前技术事项仍须落实，不能以文档已经写明代替功能完成。

真实试用以“**确认后的周菜单可直接用于供餐，无需另抄**”为核心目标。请桃子实际使用一周，观察生成结果需要改哪些地方、保存的菜单是否便于做饭时查看、发群是否仍需重抄，以及她是否愿意继续使用。记录不便和原因，再决定后续优先级；暂不预设节省分钟数或成功率。
