## 3. 账号与会话

使用微信 `login` 取得临时 code，小程序发送给本服务；服务端调用 `code2Session`，校验返回的 OpenID 与当前 AppID 下预先配置的桃子身份相符后，才建立同一经营账号的会话。没有首个访问者自动绑定或公开注册，不需要顾客手机号、UnionID 或家人协作账号。

服务端生成32字节随机会话令牌，只存 SHA-256 摘要，初始会话有效期30天；客户端持有本服务 token。每次请求检查账号启用、会话到期和撤销状态；不同设备会话关联同一账号。退出当前设备撤销当前会话，过期后重新微信登录，同一身份继续读取保存数据。更换微信身份须经营者与维护者核对后更新绑定并撤销旧会话，不通过转发链接恢复权限。

`AppSecret` 和微信 `session_key` 只在服务端流程中处理，不返回客户端，不记日志。官方成功响应可缺省 `errcode` 或为0；必须同时验证有效 `openid`。当前参考服务对 `errcode` 存在即失败的写法不可照抄，详见调研记录和契约测试要求。

所有菜池、生成、周菜单接口都在服务器鉴权并按账号限定查询；请求不接受 owner 字段。分享文字不包含管理链接或凭据。未授权身份不能因为知道 UUID、修改按钮或伪造客户端状态访问数据。

## 4. 数据实体与状态

具体字段和索引以数据模型为准，首版仅需以下五表：

| 实体 | 作用 |
| --- | --- |
| `merchants` | 单一经营账号及微信身份关联；数据库约束至多一个账号 |
| `sessions` | token 摘要、账号、到期与撤销时间；不是顾客账户 |
| `dishes` | 菜名、荤/素/汤、启用状态与版本；规范化名称唯一，含停用菜 |
| `week_plans` | 同账号同周唯一，统一结构与完整14餐 JSONB、版本和确认时间 |
| `mutation_receipts` | 菜品/周菜单写入的成功回执；与业务同事务保存，24小时去重窗口 |

周一日期标识一个自然周，按 `Asia/Shanghai` 计算。每餐三个数组保存菜品 ID 与名称快照，所在数组保存分类语义。菜池改名、改类、停用或删除不能重写历史菜单；普通保存保留同位置未变快照，新增/换入/恢复汤和整周重建均重新校验当前菜池。

去汤保留该餐汤数组，只改变 `soupOmitted`，显示与复制时隐藏；恢复时需原汤仍可用，否则要求重新选择，不自动混入失效菜。未安排的餐次三个数组为空。无需拆餐次表，也不建立订单、付款、分享历史或发布状态表。

只有服务器写入成功的菜单才有保存版本；预览和本地编辑不是持久化记录。确认与保存共用一次事务，确认只表示进入总览。确认、复制或发群后都能继续编辑；进入或取消编辑本身不写服务器，普通保存清空 confirmedAt，保存并确认则原子确定内容与确认时间。没有公布锁或解锁状态。

## 5. 生成、保存与复制

### 5.1 菜池和生成

菜名逐行拆分，去首尾空白并 NFC 规范化，过滤空行；预览只在本地，人工确认后提交。建议先识别“汤/羹”等汤特征，再识别肉、鱼、虾、鸡等荤菜特征，其余先建议素菜；这是可纠正的启发式，不推断主料、营养或忌口。无法可靠分类仍可人工改，不阻断录入。批内或菜池同名冲突列明名称，整批不写，不静默覆盖或重复建菜。

按日期、午晚餐依次生成，各分类优先选本周未用菜；不足时选择本周较久未出现、且本餐未用过的菜，同优先级随机。算法只保证同餐不重复及明确的复用优先级，不宣称最优组合。任一所需分类不足一餐时，整次生成返回422 INSUFFICIENT_DISHES，列出所需与可用数量，不返回部分预览；所有保存和确认也必须满足完整数量，不能用重复菜或错分类补齐。历史同位快照的保留规则不因此改变。

已有菜单修改周结构时，客户端先提示会覆盖已换菜和逐餐去汤等整周调整，确认才发起生成。取消或生成失败保留原编辑及保存结果；成功预览替换编辑内容但不自动保存，明确保存时使用 rebuild=true 与原 baseVersion，服务器重新校验整周。

换菜在客户端已读菜池中筛选同类、可用、与本餐不重复且不同于当前菜的候选，随机或手选只改一个位置。保存时服务端再验证，候选失效则提示刷新。新周默认独立设置、不自动复制上周，价格不加入分享字段；这些最小实现约定集中在功能规格第2.2节。

### 5.2 保存边界

所有菜品和周菜单写入先鉴权，再锁定该经营账号行，复查会话和账号状态；在同一事务检查回执、版本及业务约束，写完整实体和成功回执后才返回。单菜删除使用带 baseVersion 和幂等键的 DELETE，在同一事务移除菜池记录并保存成功回执，不删除周菜单快照，无需新增表或字段。此顺序使菜品删除或停用不能插入“校验可用→保存”之间。事务内不请求微信、不等待用户选择。

客户端每次明确写入带 UUID 幂等键与读取时的 `baseVersion`。超时重试保留键和原体，成功回执先于版本校验重放；同键不同体409。两设备旧版本保存409，不自动覆盖或合并。同周首次保存还由唯一约束保护。回执过期后仍需版本/名称唯一检查，不能盲目重试未知结果。

响应丢失可能意味着已提交，不应显示确定失败后再自动生成新写入。页面保留草稿，先完成同请求重试/核对；确认当前保存结果后再开始下一次写入。本地草稿仅驻留当前页面内存，离开前提醒；被系统终止后只保证找回已保存内容。

### 5.3 分享

进入复制预览时重新读取已保存周；读取失败提示重试，不使用旧缓存宣称最新。随后从本次读取版本生成完整年份日期、午晚餐和菜名，按荤/素/汤顺序输出，数量为0或去掉的汤不输出。未保存修改须先保存或明确放弃，不能混入已保存的分享预览。首版无价格管理，可由桃子在微信补文字。

调用平台复制成功只提示“已复制，请到微信粘贴发送”；失败保留文字允许重试。系统不读取群消息、不代发、不生成订单或已发送状态。文字是生成时的快照，菜单后来修改不会改变旧剪贴板或微信消息；允许重新编辑、保存并从保存结果生成新文字；由桃子自行通知邻居；按2026-09-21用户反馈，界面不再展示相应解释提示，不依赖系统记录是否发送。

## 6. 契约层

[OpenAPI 3.1](../../specs/022-kith-inn-menu-mvp/contracts/openapi.json) 已定义9个业务操作与2个基础探针，包括会话、菜池、周列表/详情、生成预览及整周保存。每项提供输入输出 schema、鉴权、状态码；完整语义和示例见契约说明。

相较 v0.3 的接口建议，本次减少了无需单独联网的分类预览、候选、确认和分享接口：分类/候选由客户端已有数据处理，确认作为整周写入的一项意图，分享不写业务状态。Q3 已确认不采用公布锁，因此不增加公布/解锁接口或业务状态。

Schema 管类型和格式；日期范围、同餐重复、实际数量、菜品归属、历史快照和当前可用性还需纯函数/事务校验。共享包实现阶段必须与 OpenAPI 及示例一起验证，不能只生成类型便认为接口已接通。

## 7. 初始运行目标与数据管理

以下是设计起始值，尚无实际测量，也未宣称是桃子菜池的真实规模：

| 项目 | 初始方案 / 验证方法 |
| --- | --- |
| 输入保护 | 单名1～60个 Unicode 字符，批量最多200道，菜池最多1000道含停用；每类0～10，总计1～20；请求128 KiB。达到限额提示，不截断 |
| 测试规模 | 1000道菜、104个保存周、单账号3个并发请求；此为基准样本，不是保留两年的产品承诺 |
| 服务响应预算 | 预热后读取、生成、写入分别以 p95 ≤1秒为初始门槛，至少各100次；不含微信换码、公网传输和人为停留，记录测试机器与DB环境 |
| 客户端等待 | 普通 API 10秒超时；微信换码3秒依赖超时；写入超时按未知结果安全重试，不能声称未写入 |
| 最小限流 | 登录每IP每分钟20次，登录后每账号每分钟120次，返回429及 Retry-After；先单服务实例内实现，后续扩容再评估共享计数 |
| 日志 | 只记 requestId、方法、路由模板、状态、耗时；不记录 code/token/OpenID/完整菜单；建议保存7天，上线前落实实际清理 |
| 短期数据 | 会话30天，到期/撤销记录日清；成功回执24小时，读回执也检查到期，不依赖清理定时器是否准时 |

业务数据保留与退出流程仍须上线前确认。建议在账号使用期间保留菜池和已保存周；每天一次受控加密专库备份，日备份保留7天，目标 RPO ≤24小时、RTO ≤4小时。以上是待上线审阅与演练的运营方案，不是已经具备的恢复承诺；试用前应向桃子说明最后一次保存与最后一次备份的区别。

演练在隔离库恢复账号、菜池、周菜单及历史快照，通过应用读取和完整性检查后记录时间；恢复后撤销旧会话并清理回执，避免重放恢复前成功响应。数据恢复与应用回退是两件事；仅在数据兼容时回退代码，迁移不得靠盲目逆向 SQL 撤销。

退出时停止业务访问与写入，清除在线实体、会话、含正文回执和受控备份及相关临时副本，并核查部署方可能存在的快照/PITR。若存储方不能按项目公开承诺删除，必须先解决安排或由用户明确重新约定，不能静默用“备份7天后过期”代替退出即删除，也不能提前报告删除完成。首版单账号可通过维护者操作完成，无需新增运营管理后台。
