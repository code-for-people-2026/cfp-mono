# 街坊味（Kith Inn）用户故事

版本：v0.2 · 更新时间：2026-09-13 · 依据：[PRD v0.5](PRD.md) · 状态：待审阅

本文按用户能完成的目标组织故事，业务规则以 PRD 为准，技术方案见 [TECH-SPEC.md](TECH-SPEC.md)。US-01～11 保留为稳定的故事组和追溯编号；包含多个目标的组进一步拆为带字母的子故事，例如 US-03a。子故事用于分别讨论和演示完成结果，不改变原组涵盖的需求。

下文 AC 均引用 PRD 的验收编号。一个 AC 可以由多个故事共同覆盖，不要求一条故事对应一个 AC；例如 AC-20 同时检查普通下单、桃子代下和连续订餐的信息要求。Q1～Q6 仍由 PRD 第 7 节维护，在相应功能开发前补齐受影响边界，无须为推进周菜单而先定完所有问题。

首版包含下列全部故事。组织顺序表达使用和依赖关系，不代表只交付菜单、推迟订餐或履约。

## 2. 用户故事与完成条件

### US-01 建立和维护会做的菜

**作为桃子，我希望建立可反复使用的菜品池，以便每周排菜单时不必重新输入会做的菜。**

前提／入口：首次初始化，或之后进入菜品维护。对应 PRD 5.1，验收 AC-01。

| 场景 | 完成条件 |
| --- | --- |
| 首次录入 | 每行一道菜；空清单不能提交；看到菜名及建议的荤、素、汤分类 |
| 核对清单 | 可循环调整分类、返回修改菜名；未确认前不写入菜品池 |
| 确认与维护 | 确认后看到加入数量；之后可新增、改名、改分类、停用或恢复 |
| 排菜与历史 | 只要求菜名和分类，不加主料或荤菜数量门槛；停用菜不参与新生成及换菜，历史菜单不被菜品改名或删除覆盖 |

依赖／待定：菜品不足时的排菜处理见 Q2，不通过阻止录入绕开问题。

### US-02 生成符合本周安排的菜单

**作为桃子，我希望按本周供餐安排和荤素汤数量生成七天菜单，以便先把这一周要做什么安排出来。**

前提／入口：已有可用菜品，进入“本周菜单”。对应 PRD 5.2，验收 AC-02、AC-04。

- 选择目标周和需要做的午晚餐，跳过的餐次不生成菜单。
- 本周可设两荤一素一汤，下周可设三荤一素一汤，各周按自己的统一结构生成。
- 按七个日期查看结果，同一天午晚餐放在一起。
- 同餐不重复一道菜；菜品不足以整周不重复时，允许跨餐重用并尽量隔开。

依赖／待定：新周继承和结构变更见 Q1；连一餐都排不满时怎样处理见 Q2。

### US-03 调整并确认周菜单

对应 PRD 5.2。三个子故事共同覆盖调整到回看的完整结果；公布后锁定规则与 US-04 联合检查。

#### US-03a 替换不满意的菜

**作为桃子，我希望替换指定位置的菜，以便保留满意的安排，只调整不想做的部分。**

前提：目标餐次已有菜单且尚未公布。验收 AC-05；保存后的回看与 US-03c 联验。

- 可以随机换一道，或从同类可用菜中手选；其他位置和餐次保持原样。
- 候选不与本餐其他菜重复；没有其他候选时明确提示。
- 已公布餐次不允许通过换菜被改写。

待定：随机转手选的入口、候选轮换见 Q2。

#### US-03b 去掉指定餐次的汤

**作为桃子，我希望按实际做饭安排去掉某餐的汤，以便那一餐少做一道，而不重新安排整周。**

前提：目标餐次已有菜单且尚未公布。验收 AC-03；保存后的回看与 US-03c 联验。

- 周二晚上去掉周三午餐、周五晚餐的汤后，仅这两餐不含汤；午晚餐可分别操作。
- 两餐其他菜、其他餐次、周结构和每份价格均保持原样。
- 公布前可以恢复汤；已公布餐次不允许去汤或恢复汤来改写菜单。

#### US-03c 保存并确认可照着做的周菜单

**作为桃子，我希望保存调整结果并确认周菜单，以便再次打开时直接按这份安排准备供餐，无需另抄。**

前提：已有生成或调整后的周菜单。验收 AC-05，与 US-03a、US-03b 联合检查保存结果。

- 调整可保存；确认后进入只读周菜单总览，看到最终安排。
- 再次进入、重开应用或换设备后仍能读取已保存内容。
- 确认整周不会自动公布各餐；可继续准备具体餐次的预订内容。
- 已公布餐次不会因重新生成或周设置变更而被覆盖。

待定：确认后再次编辑的入口及结构变更衔接见 Q1。能否无需另抄由真实试用检验。

### US-04 公布某餐并开放订餐

**作为桃子，我希望把确定要做的一餐公布给邻居，以便大家通过对应入口订餐，并按同一份菜单供餐。**

前提：该餐菜单已准备好；从周菜单总览继续准备餐次。对应 PRD 5.3，验收 AC-10、AC-11。

- 可核对日期、午晚餐、完整菜品、固定每份价格、截止时间和剩余份数。
- 可生成群菜单说明和小程序入口，由桃子主动发送，顾客通过对应餐次报名。
- 无需读取微信群接龙；不能把复制文案成功显示为微信消息已经发送。
- 公布后，换菜、去汤、重新生成或修改周结构均不能改写该餐菜单。
- 无法供餐时进入 US-11；仅停止接单不取消已有订单。

依赖／待定：生成文案、发群、开放和锁定的操作节点及提前处理范围见 Q3；截止及容量设置见 Q6。

### US-05 自助订一餐并查看自己的订单

**作为顾客，我希望从群菜单直接订一餐并查看订餐结果，以便确认日期、菜品、份数和收餐位置。**

前提：餐次已公布、未截止且有余量。对应 PRD 5.4，验收 AC-06、AC-15、AC-20。

- 查看菜单和每份价格，填写份数、可辨认称呼及必要位置；手机号留空仍可提交。
- 提交后直接预订成功，首次下单也不需要桃子审核或先付款。
- 可以从自己的订单中查看记录，不能查看其他顾客的订单详情。
- 同一顾客同一餐次至多一笔有效订单；重复点击或网络重试不会多出有效订单。
- 多名顾客同时订最后余量时，普通下单不会超过容量。

依赖／待定：普通份数上限和位置字段见 Q6；访问保护由技术规格确定，不能用手机号必填替代。

### US-06 私聊代下与订单归属

对应 PRD 5.4。代下、申请关联、确认归属是不同角色的目标；普通自助下单不增加这套审核。

#### US-06a 替私聊顾客记录订单

**作为桃子，我希望替私聊订餐的邻居记单并回传订单卡，以便这笔订餐进入统一的供餐清单。**

前提：桃子已与顾客确认订餐内容。验收 AC-07、AC-20。

- 可记录顾客、日期、午晚餐、份数及必要收餐位置，手机号可留空。
- 代下后可回传订单卡；记录进入相应餐次，不能因分享卡片重复计数。
- 卡片被收到或转发均不直接授予订单详情访问权。

待定：代下容量边界见 Q6，不把未定的超量候选规则当作允许超量。

#### US-06b 发起本人的订单关联

**作为顾客，我希望发起代下订单关联，以便确认归属后能在自己的订单中找到这笔记录。**

前提：已有桃子代下的订单及对应订单卡。验收 AC-07、AC-21，与 US-06c 联验。

- 可发起关联；桃子确认前无法查看该单详情。
- 转发卡片不能让接收人直接获得访问权；同名或同手机号也不会自动关联。

待定：重复顾客记录和误关联纠正见 Q5。

#### US-06c 确认代下订单属于谁

**作为桃子，我希望确认顾客发起的关联，以便订单只交给本人查看。**

前提：收到顾客的代下订单关联申请。验收 AC-07、AC-21。

- 桃子确认一次后，仅关联本人能从顾客端查看对应订单详情，并可在以后自行下单。
- 关联后，代下单仍需联系桃子修改；不会变为顾客直接创建的单餐。
- 未关联的人不能通过原订单卡继续获取详情。

待定：误确认后的纠正及重复顾客记录处理见 Q5。

### US-07 在允许范围内修改或取消订单

**作为顾客，我希望在允许范围内调整自己的订餐，以便改变计划时知道哪些能自行处理、哪些需要联系桃子。**

前提：已有订单。对应 PRD 5.4、5.5，验收 AC-09。

| 场景 | 完成条件 |
| --- | --- |
| 直接创建的单餐，尚未截止 | 可以改份数或取消；增加份数仍受余量限制 |
| 代下、连续订餐或已截止单餐 | 引导联系桃子，不能绕过限制自行修改或取消 |
| 桃子修改了自助订单 | 原创建来源保留，不因此变成代下单 |
| 取消或减量成功 | 相应有效份数、余量及配送清单同步更新 |
| 更新地址簿 | 既有订单已确认地址不被自动改写 |

待定：连续剩余餐次调整见 Q4；已截止、已送达或已收款的其他更正见 Q6。已付款停餐按 US-11，不能删除记录代替更正。

### US-08 申请并启用连续订餐

对应 PRD 5.5。未来菜单未公布也可申请；尚未生效的申请不计入有效供餐份数。

#### US-08a 提交连续订餐申请

**作为顾客，我希望一次申请连续多天的午晚餐，以便不用每天重新报名。**

前提：顾客进入连续订餐申请入口。验收 AC-18、AC-20。

- 选择开始日期、4—90 个连续天，以及午餐、晚餐或两餐；所选每餐分别填写 1—20 的整数份数。
- 天数或份数超范围、不是整数或未选餐次时不能提交。
- 提交前可核对起止日期、分餐份数、实际地址和金额：固定单价 × 每天所选份数合计 × 连续天数。
- 可辨认称呼及必要位置齐全时手机号可留空；申请提交不等于生效，可查看后续处理结果。

待定：开始日期、已知不供餐日期、已有订单及容量冲突见 Q4。

#### US-08b 替顾客建立连续订餐申请

**作为桃子，我希望替私聊的顾客建立连续订餐申请，以便把约定的多日安排统一记录下来。**

前提：桃子已与顾客确认连续订餐内容。验收 AC-18、AC-20；生效要求与 US-08d 联验 AC-08。

- 代建沿用 US-08a 的日期、餐次、整数份数和提交前核对要求，手机号同样选填。
- 代建本身不直接纳入有效份数，仍需确认微信付款并明确标记生效。

待定：Q4 的日期、重复订单和容量冲突边界同样适用。

#### US-08c 审核连续订餐申请

**作为桃子，我希望同意或拒接申请并告知结果，以便只接下能够履行的连续供餐安排。**

前提：存在待审核的连续订餐申请。验收 AC-08、AC-19。

- 同意后显示待付款，尚不计入有效份数。
- 拒接需填写简短说明，显示已拒接，并提供可复制给申请人的私聊说明。
- 拒接不计入生效份数，不自动在群内公开结果或原因。

待定：可接单的日期、已有订单及容量冲突处理见 Q4。

#### US-08d 确认微信付款并标记生效

**作为桃子，我希望收到微信付款后明确标记连续订餐生效，以便为这些约定餐次保留份数。**

前提：申请已审核通过、处于待付款，桃子已核对微信付款。验收 AC-08。

- 标记收到微信付款后才生效；待审核、待付款和已拒接均不占有效份数。
- 审核通过、截图划掉或菜单公布均不自动代替本次操作。
- 生效份数纳入约定餐次；之后公布菜单不重复计数，未来菜品及汤以各餐公布内容为准。
- 顾客能查看生效订餐和已公布菜品；到期不自动续订，调整或停止须联系桃子。

待定：容量冲突和剩余餐次调整见 Q4；停止后的退款与 US-11 联验。

### US-09 按准确份数制作并完成配送

对应 PRD 5.6，两个子故事共同验收 AC-13。

#### US-09a 查看某餐该做多少份

**作为桃子，我希望查看某餐的准确制作份数，以便不用从聊天记录重新汇总。**

前提：已确定目标餐次，存在相应订餐或自家用餐安排。验收 AC-13。

- 有效自助单、代下单和已生效连续订餐各计一次，另加自家份数。
- 待审核、待付款、已拒接及已取消的订餐不计入；取消或停止的份数退出统计。
- 余量按容量减有效顾客份数计算，最低显示为 0；自家份数只计制作，不计顾客配送和收款。

待定：容量、自家份数入口见 Q6；连续订餐容量冲突见 Q4。

#### US-09b 记录配送结果并查看进度

**作为桃子，我希望按收餐位置查看待送订单并标记送达，以便清楚知道还要送给谁。**

前提：目标餐次有需配送的有效订单。验收 AC-13，与 US-10b 联验 AC-14。

- 按小区、楼栋查看份数及订单已确认的收餐信息；自家份数不进入配送清单。
- 逐单或按组标记送达后进度一致，已送达记录可查；全部需配送订单送达后，该餐次配送完成。
- 取消或停止的份数退出待送清单；送达不自动代表收款，普通未付款订单也可完成配送。

待定：分组及未留手机号且微信联系不上时的处理见 Q6，不预设放门口、取消或视为送达。“配送中”的产生节点和餐次／订单层级见技术规格第 5.5 节的待评审建议，须在配送开发前与 PRD 5.6 同步确认。

### US-10 核对收款并跟进待核项

对应 PRD 5.7。“勾销（划掉）”沿用 PRD 的同义约定。

#### US-10a 核对微信收款截图

**作为桃子，我希望批量核对微信截图并保留待核项，以便知道哪些款项线索已经处理、哪些还需查看。**

前提：已有待处理的微信收款截图。验收 AC-16、AC-22；收款后的核对与 AC-14 联验。

| 场景 | 完成条件 |
| --- | --- |
| 一次选择多张图 | 每张独立读取姓名、金额和时间，结果及处理进度可查 |
| 唯一匹配 | 自动划掉并显示对应订单和依据，可恢复待核 |
| 多候选或无匹配 | 保留待核并说明原因；可人工核对后划掉，无须填写理由 |
| 完全识别失败 | 明确提示失败，保留原图；可重试，也可人工核对后划掉，无须补字段或理由 |
| 查看与恢复 | 能区分系统和人工划掉，所有已划掉项可恢复重新核对 |

划掉只表示该项核对完成，不表示平台验证到账；无明确匹配不擅自关联订单，连续订餐也不因此自动生效。识别服务与普通收款记录的关系由技术规格 T4 继续明确。

#### US-10b 跟进送达后尚未收款的订单

**作为桃子，我希望找到送达后尚未收款的普通订单并主动提醒，以便跟进遗漏款项。**

前提：普通订单已送达，桃子尚未收到款项。验收 AC-14。

- 未付款不阻止配送完成，桃子可主动向顾客发送付款提醒。
- 发出提醒不会自动把订单记为已收款；微信收款后可按 US-10a 使用截图核对。

待定：普通订单如何记录已收款、如何与截图划掉衔接见技术规格 T4；该规则须在收款功能开发前确定。

### US-11 停餐与退款确认

对应 PRD 5.8。系统记录取消、应退款项和顾客确认，实际通知及退款仍由桃子在微信完成。

#### US-11a 停做某餐并查明影响

**作为桃子，我希望停做某餐时看清受影响顾客、份数和应退金额，以便完成通知并逐笔退款。**

前提：桃子无法履行某餐供餐安排。验收 AC-12，与 AC-17 联验金额范围。

- 确认前可查看受影响顾客、餐次、份数和已付款部分的预计应退金额。
- 确认后关闭该餐普通报名入口，取消对应履约，移除制作配送份数，生成公告和已付款退款清单。
- 应退金额为取消份数 × 订单单价；未付款取消无退款任务，连续订餐只处理受影响餐次。
- 停餐原因及应退金额保留；其他连续餐次继续生效，公告由桃子主动发群。

待定：剩余餐次批量调整及其他已履约、已收款更正分别见 Q4、Q6。

#### US-11b 确认收到对应退款

**作为顾客，我希望核对停餐应退金额并确认收到，以便保留这笔退款的确认结果。**

前提：本人有停餐产生的应退款项。验收 AC-17；更正后的再次确认与 AC-23 联验。

- 可查看停餐原因及该餐应退金额；实际收到后确认，状态从待确认变为已确认收到。
- 停一餐不退整段连续订餐；未付款取消没有退款项。
- 未确认只表示确认尚未完成，不证明资金未到账，也不影响其他餐次。

#### US-11c 更正误点的退款确认

**作为桃子，我希望按顾客联系纠正误点确认，以便退款确认记录反映顾客的实际情况。**

前提：已付款连续订餐因停餐退款，顾客误点收到并联系桃子。验收 AC-23。

- 可恢复对应记录为待确认退款，同时保留原确认及更正记录。
- 顾客实际收到后可再次确认；更正不重复生成退款任务，也不影响其他餐次。

## 3. 联合验收

| 路径 | 串联故事 | 要检查的整体结果 |
| --- | --- | --- |
| 排好一周并公布一餐 | US-01 → US-02 → US-03 → US-04 | 七天安排可回看；逐餐去汤正确；确认与公布分开；公布餐次锁定 |
| 自助与代下后的日常供餐 | US-05／US-06 → US-07 → US-09 → US-10 | 访问归属正确，订单、制作、配送份数一致，普通单可先送后付 |
| 连续订餐停餐退款 | US-08 → US-09 → US-11 | 付款并标记后生效、份数不重复，停一餐只影响该餐，可纠正退款确认 |

按子故事检查可观察结果，再逐条通过 PRD 的 AC-01～23，最后完成上述联合路径。一个故事或 AC 通过不代表整条流程已经完成；真实试用另按 PRD 第 6 节记录效果，技术测试不能替代桃子实际使用。

## 4. 准备顺序与维护

先准备菜品池和周菜单核心故事，补齐 Q1、Q2 中与当前工作直接相关的边界；之后按依赖衔接餐次公布、订餐、连续订餐、制作配送、收款和退款。首版范围不变，这个顺序不作为删减故事的依据。

各功能开工前，须能说明该故事的入口、成功及异常结果、依赖的业务决定和验收场景；涉及待定项时，在 PRD 的 Q 表或技术规格中完成相应决定并同步引用，无须预先给不相关的后续问题编造答案。配送状态说明和普通收款 T4 分别在对应功能开发前完成。

- 新的业务决定先更新 PRD，再同步受影响故事与技术规格。
- US-01～11 及已添加的子故事编号随目标保留，不随章节顺序重排；新增目标另加编号。
- v0.2 将多目标故事拆为可分别演示的结果，补充共享 AC、前提、未定依赖和准备顺序，不新增业务范围，也未认定原型或旧代码已满足验收。
