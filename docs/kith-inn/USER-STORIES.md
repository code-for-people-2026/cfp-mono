# 街坊味（Kith Inn）用户故事

版本：v0.6 · 更新时间：2026-09-21 · 依据：[PRD v0.11](PRD.md) · 状态：本地实现待用户验收，尚未合并及微信真机验收

第一版只帮助桃子录入菜品、安排并保存周菜单，以及生成可复制到微信的菜单文字。订餐继续沿用微信；顾客不需要使用本系统。业务规则以 [PRD](PRD.md) 为准，技术方案见 [TECH-SPEC.md](TECH-SPEC.md)，实现与验证见 [功能规格](../../specs/022-kith-inn-menu-mvp/spec.md)。2026-09-20 用户已选择 1A、2A、3A，生成后的结构变更、菜品不足和分享后编辑规则按下文执行。

US 和 AC 编号用于追溯，范围收缩后不重排、不复用。一个验收条件可以由多个故事共同覆盖；下文 AC 均指 PRD 第 6 节。US-04～11 及其子故事延期，不属于本次开发或验收承诺。

## 2. 用户故事与完成条件

### US-01 建立和维护会做的菜

**作为桃子，我希望建立可反复使用的菜品池，以便每周排菜单时不必重新输入会做的菜。**

前提／入口：首次初始化，或之后进入菜品维护。对应 PRD 5.1，验收 AC-01。

| 场景 | 完成条件 |
| --- | --- |
| 首次录入 | 每行一道菜；空清单不能提交；看到菜名及建议的荤、素、汤分类 |
| 核对清单 | 可按“荤 → 素 → 汤”循环修正建议分类、返回修改菜名；未确认前不写入菜品池 |
| 确认与维护 | 确认后看到加入数量；重复菜名列明并整批不入池，可修改后再确认；之后可新增、改名、改分类、停用或恢复 |
| 排菜与回看 | 只要求菜名和分类，不加主料或荤菜数量门槛；停用菜不参与新生成及换菜，改名或停用不改写已保存菜单 |

菜池可以先录少量菜，不要求为了录入而凑满数量；生成阶段如不足一餐，按 Q2 提示补菜或调整结构，不生成缺位菜单。

### US-02 生成符合本周安排的菜单

**作为桃子，我希望按本周要做的午晚餐和荤素汤数量生成七天菜单，以便先把这一周要做什么安排出来。**

前提／入口：已有可用菜品，选择目标周。对应 PRD 5.2，验收 AC-02、AC-04。

2026-09-22 用户确认：已有菜单时，首页统一从“查看并调整这一周”进入；编辑页内提供“修改餐次和菜量”，不在首页并列放“修改周设置”。取消设置回到编辑，保留已有换菜结果；真正重新生成前提醒覆盖整周调整。

- 选择该周需要做的午晚餐，跳过的餐次不生成菜单。
- 本周可设两荤一素一汤，下周可设三荤一素一汤；各周按自己的统一结构生成，不把逐餐设置不同结构作为入口。
- 按七个日期查看结果，同一天午晚餐放在一起。
- 同餐不重复一道菜；整周尽量不重复，菜品不足时允许跨餐重用并尽量隔开。

实施默认新周独立设置，不自动复制上周菜单。已生成后改结构，须先提醒会覆盖整周换菜和去汤调整，确认后才重生成；取消或失败保留旧编辑及保存结果，成功预览需显式保存。某类不足一餐时列明所需和现有数量，不生成部分菜单；补菜或改结构后再试。

### US-03 调整并确认周菜单

对应 PRD 5.2。以下三个子故事共同覆盖从局部调整到保存回看的结果。确认、复制或实际发群后均可继续编辑，不设置公布锁或解锁动作。

#### US-03a 替换不满意的菜

**作为桃子，我希望替换指定位置的菜，以便保留满意的安排，只调整不想做的部分。**

前提：目标餐次已有可编辑的菜单。验收 AC-05；保存后的回看与 US-03c 联验。

- 可以随机换一道，或从同类可用菜中手选；其他位置和餐次保持原样。
- 换入的菜不与本餐其他菜重复，不选择已停用的菜。
- 没有其他可用候选时明确提示，不能假装已经换菜。

实施默认随机与手选分别提供入口，不维护跨次候选历史；没有候选就提示并保留原菜。确认或分享后仍可从总览继续编辑；保存后的新内容可重新确认和复制。

#### US-03b 去掉或恢复指定餐次的汤

**作为桃子，当已排好的菜单到了实际做饭时临时不做汤，我希望直接调整这一餐并保存，以便当前菜单符合实际供餐，而不重新编辑或确认整周。**

前提：本周结构含汤，目标餐次已有保存菜单；即使已确认或复制过仍可调整。验收 AC-03；保存后的回看与 US-03c、重新复制与 US-12 联验。

- 已保存菜单原有汤，周三做午饭时决定本餐不做汤：从本周入口直接选周三午餐、去汤、保存本餐调整；全程不进入整周编辑或整周确认。
- 入口和保存目标明确显示日期、午／晚餐；默认所选周内今天的已安排餐，否则为该周首个已安排餐，可以切换目标。只改变选定餐的汤；其余菜、餐次和本周结构完全不变。
- 可以恢复并保存该餐的汤。取消不写入；保存失败保留调整且不显示已保存，未知结果重试不重复写入。成功后重开与重新复制该餐文字都反映去汤／恢复结果。
- 从保存快照开始，不夹带整周或设置草稿；有未保存调整时先处理，不静默丢弃。跳过餐和周结构无汤不提供去汤操作。
- 供餐操作放在具体这一餐的菜单里，用“本餐做汤／本餐不做汤”表达；整周修改菜单页不再提供去汤／恢复按钮，仍可替换已安排的汤菜。提前删除未来餐的测试不能替代上述实际做饭场景的验收。

实施默认原汤可用则恢复；已停用或改类时重新选齐可用汤再恢复，缺菜或取消则维持去汤，不改其他菜。单餐保存沿用普通编辑规则，清除原确认状态但不要求重新确认整周才可使用或复制；后续仍可主动确认。

#### US-03c 保存并确认可照着做的周菜单

**作为桃子，我希望保存调整结果并确认周菜单，以便再次打开时直接按这份安排准备供餐，无需另抄。**

前提：已有生成或调整后的周菜单。验收 AC-05，并与 AC-25 联验保存及访问保护。

- 调整可保存；确认后进入只读周菜单总览，看到最终安排。
- 再次进入、重开应用或在另一设备使用同一经营账号后，仍能读取已保存内容，包括换菜和逐餐去汤的结果。
- 未成功保存时明确显示失败，不把未保存的调整当作已保存菜单提供给分享流程。
- 确认不会自动发送微信消息，也不会产生订餐入口或订单。

确认与保存一次完成；保存后可继续编辑，进入或返回编辑不写服务器。普通保存清除原确认状态；编辑页点击“确认 N 餐菜单”仅进入检查，最终点击“保存本周菜单”才一次保存并确认当前内容。存在未保存修改时须先保存或明确放弃再生成分享文字。能否无需另抄，由真实试用检验。

### US-12 复制一餐菜单并自行分享到微信

**作为桃子，我希望把已保存的一餐生成可复制的菜单文字，以便发到微信群时不用重新抄写菜名。**

前提／入口：选择已保存的一餐。对应 PRD 5.3，验收 AC-24。

- 生成文字前重新读取保存菜单，读取失败提示重试；文字包含完整年份日期、午餐或晚餐及该餐完整菜名，已去掉的汤不再出现。
- 桃子核对文字后主动复制，再自行切到微信发送。复制成功只表示文字已复制，不能显示为微信已经发送。
- 生成或复制失败时明确提示，可重试；失败不修改已保存菜单。
- 已生成的文字对应生成时的已保存内容，不随之后编辑自动改写；已经复制或发出的微信文字也不会被系统同步更新。
- 本故事不生成顾客菜单页面、订餐链接或菜单图片，也不读取微信群或代发消息。
- 复制页保留固定底部“排菜单／菜品池／历史”导航，不提供“继续编辑”捷径；要修改时先返回本周菜单进入编辑。通过导航离开仍保护未保存调整和结果未知的写入，不因恢复导航绕过保护。

复制或发群后可以继续编辑、保存，再从保存结果生成新文字并复制。如果此前已发到微信，由桃子自行通知邻居，旧消息不会自动更新；按2026-09-21用户反馈，页面不再展示相关解释提示。无需标记已公布或解锁。首版默认不带价格，桃子可在微信自行添加。

## 3. 联合验收与试用

以下分段检查同一条“排好、保存、回看、分享”的主路径。

| 路径 | 串联故事 | 要检查的整体结果 |
| --- | --- | --- |
| 排好并保存一周 | US-01 → US-02 → US-03a／b → US-03c | 周结构正确，跳过餐次不排菜；换菜和去汤只影响目标位置，确认后可直接查看一周安排 |
| 重开或换设备继续使用 | US-03c，联合 AC-25 | 已保存的菜品与菜单可读取；未授权者无法访问；保存失败和恢复处理符合约定；上线前验证退出删除流程 |
| 分享已保存的一餐 | US-03c → US-12 | 复制文字与已保存餐次一致，日期、午晚餐和菜名齐全，不含访问凭据；失败不损坏菜单，复制不冒充发送 |

首版验收覆盖 AC-01～05、AC-24～25。先检查各故事可观察的结果，再检查联合路径；真实试用让桃子实际安排并使用一周菜单，判断是否能直接用于供餐、无需另抄，以及是否愿意继续使用。不用订单量、收款效率或配送指标验收本版。
