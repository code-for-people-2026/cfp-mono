# Feature Specification: 商家本周菜单高保真工作区

**Feature Branch**: `codex/kith-inn-v1-menu-plan`

**Created**: 2026-07-25

**Status**: Draft

**Input**: User description: "实现 Page 3：依据本周菜单高保真参考和逐元素还原说明，在保留真实菜单生成、覆盖、换菜及预订衔接能力的前提下完成商家端本周菜单页面。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 直接查看工作周菜单 (Priority: P1)

桃子进入“菜单”后，无需输入日期即可看到适合当前经营节奏的周一至周五日期条，以及当前选中日的午餐和晚餐。她可以切换日期或前后工作周，并从卡片上直接理解菜单、价格、截止时间和预订状态。

**Why this priority**: 自动周视图是整页的信息骨架；没有它，后续生成、换菜和预订动作仍然是技术化表单，无法构成可用的经营工作区。

**Independent Test**: 准备一个包含完整、部分和空缺餐次的工作周，进入菜单页后核对默认周、默认日期、五日完成度、午晚餐卡片、价格、截止时间、状态以及前后周切换；只读浏览无需执行任何写入操作。

**Acceptance Scenarios**:

1. **Given** 当前是周一至周四，**When** 桃子进入菜单页，**Then** 页面展示当前工作周并选中该周第一个尚未过去的工作日。
2. **Given** 当前是周五至周日，**When** 桃子进入菜单页，**Then** 页面展示下一个工作周并默认选中周一。
3. **Given** 展示的工作周包含不同完成状态，**When** 桃子查看五日日期条，**Then** 她可以区分没有菜单、只完成一个餐次、两个餐次均完成以及已有开放餐次的日期。
4. **Given** 所选日期的午餐或晚餐已有菜单，**When** 桃子查看对应卡片，**Then** 菜名使用生成时保存的快照，并显示真实价格、截止时间和经营状态。
5. **Given** 所选日期缺少午餐或晚餐，**When** 桃子查看对应位置，**Then** 页面仍显示该餐次的空缺卡片和明确的生成入口。
6. **Given** 桃子快速切换多个工作周，**When** 较早请求晚于较新请求返回，**Then** 页面保留最后选择的工作周，不被旧结果覆盖。
7. **Given** 当前周已有可见数据，**When** 页面进行返回刷新或轻量重试，**Then** 旧数据在刷新期间继续可读，不出现整页闪白。
8. **Given** 桃子切换到过去或未来工作周，**When** 目标周加载，**Then** 页面默认选择该周周一；切回当前周时重新选择第一个尚未过去的工作日。
9. **Given** 页面保持打开且某个 `open` 餐次到达截止时刻，**When** 业务时间跨过截止点，**Then** 页面无需用户刷新即可立即把该餐次和日期摘要更新为已截止。

### User Story 2 - 生成和补齐菜单 (Priority: P2)

桃子可以为单个缺失餐次生成菜单，也可以一次生成或补齐工作周午晚餐；已有草稿菜单需要重新生成时，页面先列出将被覆盖的具体目标并要求确认。

**Why this priority**: 菜单生成是本页核心写入价值；它依赖 User Story 1 的工作周和餐次上下文，但可独立通过菜单写入结果验收。

**Independent Test**: 使用菜品数量充足的商家，从空工作周分别生成单餐和整周，再制造部分空缺验证只补缺失目标；对已有草稿执行重新生成并检查覆盖确认，对不可编辑餐次确认不会进入覆盖目标。

**Acceptance Scenarios**:

1. **Given** 所选日期的某个餐次没有菜单，**When** 桃子点击“生成午餐”或“生成晚餐”，**Then** 只生成该目标并保留同日另一个餐次。
2. **Given** 工作周十个餐次均缺失，**When** 桃子点击“生成本周午晚餐”，**Then** 系统为周一至周五的午餐和晚餐生成完整菜单。
3. **Given** 工作周只缺部分餐次，**When** 桃子点击“补齐本周菜单”，**Then** 只生成缺失目标，不覆盖已有菜单。
4. **Given** 桃子要求重新生成已有草稿，**When** 系统发现目标已有菜单，**Then** 页面列出将被覆盖的日期和午晚餐，并在桃子确认前保持原菜单不变。
5. **Given** 重新生成目标中包含 `open`（包括已截止）或 `closed` 餐次，或餐次在生成期间由 `draft` 变为 `open`，**When** 页面或服务端处理目标，**Then** 持久化写入边界按最新状态拒绝修改，这些餐次不进入覆盖写入；截止时间已过的 `draft` 仍可编辑菜单。
6. **Given** 菜品池分类数量不足，**When** 桃子生成菜单，**Then** 页面说明每类缺少数量、不写入不完整菜单，并提供前往菜品库的入口。
7. **Given** 分类数量足够但避重偏好无法全部满足，**When** 菜单成功生成，**Then** 页面保留完整菜单并说明本次放宽的偏好。

### User Story 3 - 调整一道菜 (Priority: P3)

桃子对某个仍可编辑的菜单不满意时，可以先查看当前五道菜并选择要换掉的一道；系统自动选择同类替代菜，只更新目标菜单项。

**Why this priority**: 换菜提升菜单可控性，但不阻塞整周菜单从无到有，因此排在生成之后。

**Independent Test**: 对一个草稿餐次依次选择五道菜中的一道执行替换，确认其余四道保持不变；再制造同类无候选场景，确认原菜单保持不变并出现补充菜品引导。

**Acceptance Scenarios**:

1. **Given** 一个草稿餐次已有五道菜，**When** 桃子点击“换一道”，**Then** 页面列出当前五道菜并要求选择要换掉的菜。
2. **Given** 桃子选择了一道菜且存在同类候选，**When** 替换成功，**Then** 只更新目标菜单项，另外四道菜和当前日期选择保持不变。
3. **Given** 没有合适的同类候选，**When** 替换失败，**Then** 原菜单保持完整，并提示先补充菜品库。
4. **Given** 当前餐次为 `open`（包括已截止）或 `closed`，**When** 桃子查看卡片或尝试调用写入接口，**Then** 页面不提供换菜或重新生成入口，服务端也拒绝修改菜单。
5. **Given** 一个餐次正在换菜，**When** 桃子操作其他日期，**Then** 只锁定当前餐次的换菜操作，其他日期仍可浏览。

---

### User Story 4 - 衔接预订配置和分享 (Priority: P4)

菜单排好后，桃子可以从当前工作周或指定餐次自然进入价格、截止时间、开放预订和分享流程；返回菜单页时立即看到最新配置。

**Why this priority**: 该流程把菜单安排连接到真实经营动作，但价格与开放预订已有独立工作区，不应在本页重复实现。

**Independent Test**: 从已排好菜单但未配置的餐次进入预订配置，设置价格、截止时间并开放；返回后核对当前周、选中日期、状态、价格和截止时间已刷新，再从已有开放餐次进入预订与分享。

**Acceptance Scenarios**:

1. **Given** 本周菜单完整但仍有餐次待配置，**When** 桃子点击底部主操作，**Then** 页面进入预订配置并尽可能保留当前周和餐次上下文。
2. **Given** 桃子从某餐次点击“设置价格与截止时间”，**When** 配置页打开，**Then** 目标日期和餐次无需再次从空白状态查找。
3. **Given** 桃子完成配置后返回菜单页，**When** 页面重新可见，**Then** 当前周数据轻量刷新并显示最新价格、截止时间和状态。
4. **Given** 本周已经有开放餐次，**When** 桃子点击“查看预订与分享”，**Then** 页面进入现有预订与分享工作区。
5. **Given** 功能开关启用了接龙兜底，**When** 桃子寻找低优先级工具，**Then** 接龙入口仍可达；开关关闭时该入口完全不显示。

### Edge Cases

- 设备使用非上海时区或跨越 UTC 日期边界时，业务日期仍按 `Asia/Shanghai` 显示且不得偏移一天。
- 月末、年末、闰年和工作周跨月时，周一至周五范围和前后周切换仍保持连续。
- 首次加载失败时，页面显示可重试错误态；刷新失败且已有数据时，旧数据继续可读并显示轻量错误说明。
- 单个午餐请求失败时，晚餐卡片及其他日期仍保持可用；整周生成发生非分类不足错误时必须重载当前周，不得把可能的局部持久化误报为整周完成或零写入。
- 快速切周、返回刷新和生成结果并发时，只有与当前周和当前操作匹配的结果可以更新页面。
- 菜单项名称或主料很长时，卡片可自然换行，但操作按钮、状态和底部导航不得被挤出可操作区域。
- 价格为空时显示商家默认价，不显示零元；截止时间为空时明确显示未设置。
- `open` 餐次截止时间刚刚到达时立即显示“已截止”并保持只读；`draft` 的旧截止时间已过时显示“待设置”，但仍可修改菜单。
- 同一餐次的换菜或生成被重复点击时，只接受一个进行中的操作。
- 商家会话失效、成员停用或商家暂停时，受保护操作失败并返回登录，不保留可继续写入的假状态。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 页面必须在进入时自动展示一个周一至周五的工作周，不要求用户输入日期。
- **FR-002**: 默认工作周必须遵循周一至周四显示当前周、周五至周日显示下一周的规则。
- **FR-003**: 当前工作周的默认日期必须是该周第一个尚未过去的工作日；过去周和未来周默认选择周一。每次前后周切换都按目标周重新计算默认日期，不跨周保留星期索引。
- **FR-004**: 所有业务日期和截止状态必须按 `Asia/Shanghai` 计算，不能由设备时区改变业务日。
- **FR-005**: 用户必须能够切换上一工作周和下一工作周，并始终看到明确的五日日期范围。
- **FR-006**: 页面必须以五个等宽日期项展示周一至周五，并分别表达每一天的菜单完成度和预订生命周期信号；两者不得互相覆盖，例如午餐已开放且晚餐缺失时必须同时表达“部分完成”和“预订中”。
- **FR-007**: 切换工作日必须只更新所选日期的午餐、晚餐展示，不得重新加载整个工作周。
- **FR-008**: 快速切换工作周时必须以后发请求为准，旧响应不得覆盖当前选择。
- **FR-009**: 页面从其他经营页面返回时必须刷新当前周；已有数据在刷新期间继续可见。
- **FR-010**: 所选日期必须始终展示午餐和晚餐两个位置，即使对应餐次尚不存在。
- **FR-011**: 已有菜单必须展示保存时的五道菜快照，不能根据当前菜品库重建历史名称。
- **FR-012**: 餐次卡片必须显示真实价格、截止时间和状态；空价格显示商家默认价，空截止时间显示未设置。
- **FR-013**: 页面必须按明确优先级区分未排菜单、待设置、待开放、预订中、已截止和已关闭；空价格表示商家默认价，不单独构成未配置。页面保持打开时必须调度到下一个 `open` 餐次截止点主动重算状态，不依赖用户刷新。
- **FR-014**: `open`（包括已截止）和 `closed` 餐次必须在前端、业务服务和 CMS/Payload 持久化写入边界保持菜单只读；写入边界必须按提交时的最新状态拒绝菜单变更，不能只依赖读取后的路由预检查；`draft` 不因旧截止时间已过而失去菜单编辑能力。
- **FR-015**: 用户必须能够只生成一个缺失午餐或晚餐，且不影响同日另一餐次。
- **FR-016**: 用户必须能够为完全空缺的工作周生成周一至周五全部午晚餐。
- **FR-017**: 用户必须能够只补齐工作周缺失餐次，已有菜单不得进入补齐目标。
- **FR-018**: 重新生成已有草稿前必须列出将被覆盖的日期和餐次并取得明确确认。
- **FR-019**: 取消覆盖确认必须保留原菜单、当前工作周和所选日期。
- **FR-020**: 菜品池不足时不得创建不完整菜单，页面必须显示具体分类缺口并提供菜品库入口。
- **FR-021**: 菜单生成成功但放宽避重偏好时，页面必须说明被放宽的规则；整周响应只有聚合规则时使用周级提示，不虚构受影响餐次。
- **FR-022**: 草稿餐次必须允许用户从当前五道菜中选择要换掉的一道，替代菜由系统自动选择。
- **FR-023**: 换菜成功只能替换目标菜单项；无候选时原菜单必须保持不变。
- **FR-024**: 生成和换菜操作只能锁定相关餐次或周主操作，无关日期仍可浏览。
- **FR-025**: 底部主操作必须按“缺失目标 → 草稿配置/开放 → 查看预订与分享”的优先级显示生成整周、补齐本周、进入配置或查看预订与分享。
- **FR-026**: 菜单生成成功即视为已保存；页面不得把菜单生成、价格设置和开放预订伪装成一次原子操作。
- **FR-027**: 用户必须能够从草稿餐次进入现有价格和截止时间配置流程，并携带当前周或目标餐次上下文。
- **FR-028**: 用户必须能够从已有开放餐次的工作周进入现有预订与分享流程。
- **FR-029**: 接龙导入仅在既有功能开关启用时通过低优先级入口可达，不能占据菜单主线。
- **FR-030**: 页面必须保留现有认证失败、成员停用和商家暂停处理，不得绕过商家隔离。
- **FR-031**: 页面必须在首次加载、刷新、空周、部分完成、全部完成、加载失败、单餐生成、整周生成、覆盖确认、换菜、菜品池不足、规则放宽和只读状态下提供明确反馈。
- **FR-032**: 页面底部必须复用“今日 / 菜品 / 菜单 / 订单”主导航并正确激活“菜单”。
- **FR-033**: 页面内容必须在目标移动端宽度下可滚动、无横向溢出，固定主操作和导航不得永久遮挡午晚餐内容。
- **FR-034**: 本功能不得新增指定替换菜、拖拽排序、自定义菜品结构、菜单图片、库存、成本、版本历史、多人协作、AI 菜单或在线支付。
- **FR-035**: 覆盖确认必须区分原始生成目标和后端返回的已有目标；确认层只展示已有目标，确认后提交原始目标，切周或上下文失效时清除确认。
- **FR-036**: 菜品池分类最低数量固定为荤菜 2、素菜 2、汤 1，不按批量餐次数放大；数量足够组成一餐但无法全周避重时走规则放宽。
- **FR-037**: 每次生成或换菜必须记录目标工作周和每个目标键的单调 mutation revision，并使该周更早发出的在途读取失效；同一目标只接受匹配 revision 的响应，不同目标的并行响应不得互相作废。用户切周、发起写操作或写操作提交后，旧读取/写入响应不得合并餐次、覆盖提示或清除当前确认状态，非菜品池失败仍需按其目标周重新加载真实状态。
- **FR-038**: 单目标失败或任何写入前失败必须保留原菜单；多目标逐餐次写入发生中途失败时允许已成功目标保留，但每个已持久化餐次仍必须是完整五道菜。页面必须重载目标周并明确说明“部分目标可能已保存”，不得宣称整批成功、零写入或已回滚。

### Key Entities

- **工作周**: 一个按上海业务日期定义的周一至周五范围，包含五个工作日、当前选中日以及上一周/下一周关系。
- **工作日摘要**: 表示某工作日午餐和晚餐的存在、完成度、开放状态，用于日期条状态表达。
- **餐次**: 当前商家某一业务日期的午餐或晚餐，包含菜单快照、价格、截止时间和预订状态。
- **菜单项快照**: 餐次生成时保存的菜品引用、菜名、主料和分类；后续菜品变化不改写快照。
- **生成目标**: 一组需要生成或覆盖的日期与餐次；补齐目标只包含缺失餐次，覆盖目标只包含可编辑草稿。
- **覆盖确认**: 在写入前展示目标列表和影响的临时决策；取消不改变餐次。
- **规则放宽说明**: 菜单完整生成后，记录本次未能满足的近期或同周避重偏好。

### Scope Boundaries

- 本功能只改造 v1 商家“本周菜单”及进入现有预订配置的必要衔接，不改变菜单生成规则和数据模型。
- 本功能不在菜单页复制完整的预订批次、分享创建或订单管理表单。
- 本功能不改变旧版产品、其他项目或共享内容管理后台的身份与数据边界。
- 本功能不承诺真实微信设备上的视觉验收可由浏览器自动化替代；跨端构建与 H5 自动化是代码门禁，真机验收另行记录。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 已登录商家进入菜单页后，无需输入日期或执行额外查询，即可在 3 秒内看到目标工作周、五日日期条以及所选日午晚餐状态。
- **SC-002**: 在空工作周、部分完成周和完整工作周三种场景中，用户均能在一次页面访问内正确完成对应的生成整周、补齐本周或进入预订配置任务。
