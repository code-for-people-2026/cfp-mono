# Feature Specification: Kith Inn v1 营业预订与分享定位

**Feature Branch**: `codex/kith-inn-v1-booking-availability-contract`

**Created**: 2026-07-26

**Status**: In Progress（商家核心功能已交付；T027–T031 待完成）

**Input**: 重构商家端 Page 4，使商家能设置默认价格、逐餐或批量开放/停止未来餐次、标记整天或某餐打烊，并把小程序卡片定位到某天或某餐；未设置餐次对顾客不可见，顾客端实时浏览留待后续实现。

## User Scenarios & Testing

### User Story 1 - 安排未来营业与预订 (Priority: P1)

商家查看选定工作周，设置默认套餐价，在逐餐覆盖价格和截止时间后，单独或批量开放、停止餐次；不营业时可标记整天或某餐打烊。

**Why this priority**: 真实餐次状态是顾客可见性和分享入口的共同事实源。

**Independent Test**: 准备含未设置、开放、截止、停止和打烊状态的工作周，完成单餐及批量操作并核对每餐结果和顾客可见性模型。

**Acceptance Scenarios**:

1. **Given** 商家有默认价且餐次菜单完整，**When** 使用默认价设置未来截止时间并开放，**Then** 该餐保存明确价格并成为可预订状态。
2. **Given** 多个餐次混有不完整配置，**When** 批量开放，**Then** 系统逐餐报告成功或具体失败，不宣称整体原子成功。
3. **Given** 某天或某餐不营业，**When** 商家标记打烊，**Then** 它与“停止预订”保持不同语义，且可取消打烊后重新配置。
4. **Given** 餐次已有顾客预订，**When** 商家尝试标记打烊，**Then** 系统阻止静默变更并提示先处理订单。

---

### User Story 2 - 分享某天或某餐 (Priority: P2)

商家从已经开放的餐次选择一个日期或一个具体午晚餐，生成并分享微信小程序卡片；卡片只提供初始定位，不定义顾客可见范围。

**Why this priority**: 分享应成为实时预订应用的快捷入口，而不是平行的餐次权限系统。

**Independent Test**: 分别分享仅午餐、午晚餐同日和包含已停止目标的卡片，核对标题、公开标识、日期及餐次定位。

**Acceptance Scenarios**:

1. **Given** 某天至少一个餐次已开放，**When** 商家分享这一天，**Then** 卡片携带该日期定位并调起微信原生分享。
2. **Given** 某餐已开放，**When** 商家分享这一餐，**Then** 卡片同时携带日期和午晚餐定位。
3. **Given** 卡片创建后餐次状态变化，**When** 顾客以后打开，**Then** 定位信息不伪装成发布快照，后续顾客端可按实时状态呈现。

---

### User Story 3 - 查看和管理分享入口 (Priority: P3)

商家创建卡片后进入高保真成功态，并可从紧凑历史列表打开实时详情、再次分享或停用旧入口。

**Why this priority**: 商家需要在重新传播前确认入口及当前餐次，避免分享错误批次。

**Independent Test**: 创建、查看、再次分享和停用开放/关闭/归档入口，核对紧凑历史和完整详情的状态语义。

**Acceptance Scenarios**:

1. **Given** 卡片创建成功，**When** 页面切换到分享态，**Then** 展示商家、标题、定位日期、餐次数、价格和截止摘要。
2. **Given** 历史入口位于其他工作周，**When** 商家打开详情，**Then** 系统按实时餐次数据展示，不猜测缺失信息。

### Edge Cases

- 整天打烊不得与当天开放餐次并存；某餐打烊不得与该餐开放并存。
- 未设置或仅为草稿的餐次不进入顾客可见集合；已截止、停止或明确打烊可见但不可预订。
- 批量写入发生部分失败时保留成功结果与失败草稿，重复点击不得重复写入。
- 分享目标后来停止、截止或打烊时，公开定位仍可解析，不显示虚假的“链接失效”。
- 修改默认价不得隐式改动已经开放餐次的明确价格。

## Requirements

### Functional Requirements

- **FR-001**: 商家必须能读取和修改本商家的默认套餐价。
- **FR-002**: 默认价必须作为配置模板；开放餐次时必须保存最终明确价格。
- **FR-003**: 商家必须能逐餐设置价格、未来截止时间和开放状态。
- **FR-004**: 商家必须能选择多个餐次批量开放或停止，并得到逐餐结果。
- **FR-005**: 未设置餐次必须保持隐藏，不得自动等同于打烊。
- **FR-006**: 商家必须能标记整天打烊或仅午餐/晚餐打烊；打烊必须独立于餐次预订状态。
- **FR-007**: 有已有预订的范围不得被静默标记打烊。
- **FR-008**: 本期必须在共享领域契约中固化顾客可见性规则：草稿隐藏；开放可订；截止、停止和明确打烊可见但不可订；顾客端全量浏览和打烊原因 UI 接线留待后续规格。
- **FR-009**: 商家必须能分享一个日期或一个日期加午晚餐的定位。
- **FR-010**: 分享目标必须是微信小程序原生卡片，不包含 H5 公开链接。
- **FR-011**: 本期必须固化“分享定位不定义未来 seller 范围可见性”的领域契约；兼容期公开批次仍作为现有顾客流程的访问边界，seller 范围实时浏览接线留待后续规格。
- **FR-012**: 兼容期内现有公开批次标识和顾客流程必须继续工作，顾客端全量实时浏览不在本次 UI 范围。
- **FR-013**: Page 4 必须区分加载、局部失败、空、配置、批量处理中、分享成功、关闭和归档状态。
- **FR-014**: 页面必须防止配置、批量开放、创建入口和关闭入口的重复提交。
- **FR-015**: 历史入口必须先以紧凑列表呈现，完整详情按需加载当前餐次信息。
- **FR-016**: Page 4 必须保持流程子页，不增加商家底部一级导航，并按来源返回首页或菜单。

### Key Entities

- **商家预订设置**: 商家的默认套餐价；只作用于尚未开放餐次的配置模板。
- **餐次**: 日期与午晚餐组合，保存菜单、明确价格、截止时间及预订状态。
- **营业关闭记录**: 商家明确不营业的日期或餐次；日期级覆盖当天午晚餐。
- **分享定位**: 公开随机标识、商家、标题及日期/可选午晚餐定位；兼容现有批次记录。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 商家能在 3 分钟内完成一周餐次的默认价应用、个别改价和批量开放。
- **SC-002**: 单餐、整天及混合打烊场景的顾客可见性判断在全部验收样例中保持一致。
- **SC-003**: 连续触发任一写操作时，每个目标最多产生一次有效变更。
- **SC-004**: 商家能在创建入口后两步内调起指定日期或餐次的小程序卡片分享。
- **SC-005**: 375×812 视口下所有要求状态均无横向溢出、遮挡或不可达操作。

## Assumptions

- 初始范围仍按菜单页传入的周一至周五工作周，商家可通过周导航处理以后工作周。
- “停止预订”不取消已有订单；“打烊”遇到已有订单时先阻止，订单取消与通知流程另行设计。
- 停止的餐次在截止时间前、配置仍有效时允许重新开放；取消打烊不会自动开放预订。
- 顾客直接打开应用时如何选择商家留给顾客端后续规格，本次只固化 seller 范围内的实时可见性规则。
