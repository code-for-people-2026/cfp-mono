### 1.1 本轮界面验收

- 手机内容区同时展示三天，横向查看七天，按午晚餐分组，提供“荤菜／全部”切换。跳过餐、去汤、零数量分类、长菜名及允许的最大菜量须能正确展示和操作。
- 点中具体日期、餐次的一道菜后，明确显示选中位置及“换一道／自己选”；只替换该同类菜位，保留其他草稿调整。逐餐去汤、恢复和周设置保持可达。
- 固定入口为“排菜单／菜品池／历史”。空菜池引导录入自己的菜，再设置并生成；已有菜池可直接排菜。离开有修改页面须确认，取消保留输入；批量录入及写入结果未知时的保护不得因导航失效。重新进入历史须读取最新保存记录。
- 确认与保存仍一次完成，确认总览以“去复制菜单”为主动作，并允许继续编辑；沿用独立的选餐、预览、主动复制状态。
- 本轮不引入家庭人数、预设图片菜库、复制到下周、空的“我的”页或新接口及数据表。Q1～Q3 和现有菜池、菜单数据保持不变。

## 2. 业务决定与实现默认值

### 2.1 已确认的三个业务决定

2026-09-20 用户在逐项了解具体情境后回复“1a，2a，3a”。下列规则已确认，Q 编号继续用于追溯。

| 编号 / 选择 | 具体场景 | 正式规则 |
| --- | --- | --- |
| Q1 / 1A | 已排好两荤一素一汤，并换过菜、去过某餐的汤，现在想改成三荤一素一汤 | 先提醒将覆盖整周换菜、逐餐去汤等调整；确认才重生成。取消或失败保留原编辑及服务器记录；成功后检查并显式保存才覆盖已保存菜单 |
| Q2 / 2A | 一餐需要两道荤菜，但菜池只有一道可用荤菜 | 列明分类、所需和现有数量，整次不生成。补菜或改结构后重试，不生成或保存缺位菜单；足以一餐但不足整周不重复时仍允许跨餐重用 |
| Q3 / 3A | 周三午餐已发群，后来买不到清蒸鱼，想换成黄焖鸡 | 确认、复制或发群后均可继续编辑、保存并重新复制；提示桃子自行通知邻居，旧微信文字不自动更新。没有公布、锁定或解锁动作 |

上述业务选择已同步 PRD、用户故事、数据模型与接口。它们不再是开发前待答项；实现、性能和真实上线条件仍须验证。

### 2.2 本稿采用的最小实现约定

这些是本次补规格提出的交互和工程默认值，可以在评审时调整，不冒充桃子已经验证的习惯。

- 新周独立设置，不自动生成或复制上周菜品，也不新增“常用模板”管理。页面可以保留当前尚未提交的表单；自动继承跨周设置留到试用后。
- 换菜入口提供“随机换一道”和“选择其他菜”。手选候选按名称排序；随机在本餐合法候选中抽取，排除当前菜，不维护跨次候选轮换历史。
- 去汤针对该餐全部汤位。恢复时优先使用隐藏的原汤；若其中有已停用或改类菜，提示重新选择可用汤，凑齐本周汤数量后一次恢复，取消则维持去汤。汤池仍不足时不恢复，不改其他菜。
- 分享只带日期、午晚餐和菜名，不带价格；需要价格时桃子可以在微信中自行添加。首版不建设固定单价设置。
- 确认是保存并进入只读总览，总览提供“继续编辑”。进入或取消编辑不改服务器状态；普通保存编辑结果清除原确认时间，点击“确认周菜单”则保存并确认同一内容。再次编辑已保存菜单时统一提示“如之前已发到微信，请自行通知邻居，旧消息不会自动更新”，无需记录是否实际发送。
- 只分享服务器已保存版本。存在未保存修改时阻止生成新的分享预览并提示先保存或放弃修改；不默认替桃子丢弃草稿。无未保存修改时重新读取已保存周再生成餐次文字，读取失败提示重试，不要求额外“发送确认”。

## 3. 用户场景与优先级

所有下列场景均属于首版。P1 指先完成核心闭环，P2 指随后完成交付闭环，不表示可以省略分享。

### P1：建立菜品池（US-01，AC-01）

Given 桃子粘贴每行一个菜名，When 系统形成分类预览，Then 菜品尚未进入菜池；桃子可循环纠正分类、返回改名后确认。

Given 桃子确认一批无重复的菜，When 保存成功，Then 显示本次新增数量；超时后重试同一请求不新增第二批。批内或菜池已有同名菜时列明名称，整批不写入，桃子修改后以新请求提交；已停用同名菜提示去维护中恢复。

Given 某菜已用于保存的周菜单，When 桃子改名、改类或停用该菜，Then 历史菜单的名称和分类不变；后续生成、换入或恢复汤重新检查当前可用性。

### P1：生成一周（US-02，AC-02、AC-04）

Given 本周两荤一素一汤且下周三荤一素一汤，When 分别生成，Then 每周遵守各自结构，每天午晚餐按日期组织，跳过餐次不出现菜品。

Given 一餐所需分类均足够，When 生成整周，Then 同餐无重复；优先整周未用菜，再选择本周较久未出现的菜。整周菜不够时允许跨餐重用，不混用荤、素、汤凑数。连一餐都不够时返回具体缺少分类及所需/现有数量，整次不生成，补菜或改结构后才能重试。

Given 已有菜单且换过菜、去过汤，When 桃子修改周结构，Then 系统提示重排会覆盖这些整周调整，确认才开始生成；取消或生成失败保留原编辑和服务器菜单，成功仅更新预览，显式保存才覆盖原记录。

### P1：局部调整并保存（US-03a／b／c，AC-03、AC-05）

Given 已有可编辑菜单，When 随机或手选换掉一个菜位，Then 只该位置改变；若没有合法候选，提示并保留原菜。

Given 周二晚上编辑本周，When 去掉周三午餐、周五晚餐的汤，Then 仅这两餐隐藏汤，周结构、荤素菜和其他餐次完全不变；恢复行为按 2.2。

Given 两台设备都读到 version=3，When 第一台保存得到4、第二台仍按3保存，Then 第二台收到版本冲突，保留本地草稿并提示重新读取；不能静默覆盖第一台。

Given 桃子保存或确认，When 网络失败或服务失败，Then 不显示已保存，原完整记录不变；当提交已成功但响应丢失，原请求安全重试返回原结果。确认与内容保存一次完成，不能确认旧版却展示未保存新版。

Given 读取已确认菜单，When 进入编辑后取消，Then 原内容和确认时间不变；普通保存编辑结果清除确认时间，保存并确认才对新内容设确认时间。不得因已确认或复制过而拒绝合法编辑。

### P2：回看并复制某餐（US-12，AC-24）

Given 桃子重新登录同一微信账号或换设备，When 选择一个已保存周，Then 看见原保存菜单及去汤结果；本地临时预览不是跨设备保存内容。

确认后的周总览以“去复制菜单”为主动作，进入独立的“确认与分享”状态，选择本周已安排日期及午晚餐、预览并主动复制；可返回周菜单或继续编辑。逐餐入口复用同一状态，不能让下一步只藏在日期展开项中。

Given 选择已保存的某餐，When 生成文字，Then 使用明确日期、午餐或晚餐、完整菜名，去掉的汤不出现；跳过的餐次没有复制入口。

Given 桃子主动点击复制，When 平台报告成功，Then 显示“已复制，请到微信粘贴发送”；失败保留预览并允许重试。系统不声称已发送，不产生订单。复制或发群后仍可编辑，保存后生成新文字重新复制，提醒自行通知邻居，原微信消息不变。

### 共同保障（全部故事，AC-25）

Given 未获桃子权限的微信用户，When 请求登录或直接请求任何内部接口，Then 不创建经营账号、不返回菜池或菜单。修改客户端角色、对象 ID 或请求体不能取得权限。

Given 已有真实保存记录，When 运行恢复演练，Then 在隔离库找回菜池、周菜单快照和账号关联；备份文件存在不等于演练通过。退出删除必须覆盖在线数据、会话、含数据回执和备份，验证后才能宣称完成。

## 5. 工程约束和异常反馈

- 日期按 `Asia/Shanghai` 解释，API 使用 ISO 日期，不用毫秒时间戳代表餐期。`2026-09-21` 为周一，目标周到 `2026-09-27`，每天先午后晚。日历运算必须跨月、跨年及闰日正确。
- 每类数量先设0～10、总数量1～20；每次最多200道、菜池最多1000道（含停用）、单名1～60个 Unicode 字符、请求128 KiB。这些是初始保护值，非已调研出的经营规模；达到限额说明原因，不截断。实现前可按实际菜池调整并同步契约。
- 所有写入先做输入和权限校验，再使用事务；错误返回动作相关提示，不显示原始数据库或微信响应。详情见契约错误表。
- 本地未保存草稿只保留在当前页面内存，不承诺强制退出后恢复；离开编辑页前有未保存提示。小程序被系统杀掉后只能恢复服务器已保存内容，页面须持续标明“未保存”。
- 不把 UI 隐藏、H5 mock、剪贴板成功或数据库迁移脚本存在当作权限、真机发送、跨设备保存或恢复完成的证据。

## 6. 完成定义

自动化必须覆盖正常路径之外的同餐重复、跨周日期、去汤无旁路修改、历史快照、并发写入、重复提交和跨账号读取。具体用例在 [contracts/README.md](contracts/README.md) 与 [quickstart.md](quickstart.md)。

试用目标仍是桃子实际用一周后，确认的菜单能直接照着做、分享无需重抄。性能初始测试预算与恢复建议见 TECH-SPEC，不将未测量的数值写成实测结论。

Q1～Q3 业务决定已完成；实现任务完成、仓库门禁通过、微信真机与恢复删除演练分别取得证据后，才能说具备首版交付条件。原型调整或本地试用通过不替代这些交付证据。
