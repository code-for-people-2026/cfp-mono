# 街坊味菜单 MVP：数据模型

更新时间：2026-09-20 · 状态：实施设计，尚未建表、迁移或部署

依据：[PRD](../../docs/kith-inn/PRD.md)、[功能规格](spec.md)、[接口契约](contracts/openapi.json)。本文规定存储、不变量和事务边界。Q1～Q3 已于 2026-09-20 按用户选择 1A、2A、3A 确定：改结构经提醒确认后整周重生成；菜不足填满一餐时不生成；确认或分享后仍可编辑。编号保留作决策追溯。

## 1. 存储边界

采用独立 PostgreSQL 数据库承载本产品，PostgreSQL 17 是本地与 CI 的方案验收基线；托管环境的实际版本、权限与恢复能力仍须上线前验证。服务使用 Node.js 22、`node:http` 和 `pg`，请求及响应由共享 Zod 契约校验。

首版只有 `merchants`、`sessions`、`dishes`、`week_plans`、`mutation_receipts` 五张业务及运行支撑表。不复用另一产品的账号或菜单表，不建订单、顾客、支付、公布、分享历史或独立确认表。周内餐次和菜位作为单个周菜单的 JSONB 内容原子保存。

业务日期采用 `Asia/Shanghai` 的自然日，用 PostgreSQL `date` 和接口 `YYYY-MM-DD` 表示；操作时间用 `timestamptz`，接口使用带 `Z` 的 UTC 时间。所有 ID 为 UUID，版本为从 1 开始的正整数，由服务端生成；首次写周请求中的 `baseVersion: 0` 不是已保存版本。

## 2. 实体、字段与约束

### 2.1 经营账号 `merchants`

| 字段 | 类型与规则 |
| --- | --- |
| `id` | UUID 主键 |
| `singleton` | boolean，固定为 `true`，非空且唯一，保证首版至多一个经营账号 |
| `app_id`、`openid` | text，非空；组合唯一；微信身份关联只由服务端登录流程写入 |
| `active` | boolean，非空；停用后禁止创建经营会话或访问业务数据 |
| `created_at`、`updated_at` | timestamptz，服务端记录 |

首次账号建立须匹配部署配置中预先授权的微信身份，不能把首个登录者自动登记为桃子。客户端不能提交 `merchant_id` 选择账号，也不能修改授权名单。微信 `AppSecret` 与 `session_key` 不进入此表或业务响应；不要求 UnionID、手机号或顾客身份。

### 2.2 登录会话 `sessions`

| 字段 | 类型与规则 |
| --- | --- |
| `token_hash` | bytea 主键，长度 32 字节；随机 bearer token 的 SHA-256 摘要 |
| `merchant_id` | UUID，外键关联经营账号，非空 |
| `created_at`、`expires_at` | timestamptz，非空；到期时间晚于创建时间，由服务端设定 |
| `revoked_at` | timestamptz，可空；非空即失效 |

token 由密码学安全随机源生成 32 字节，再进行 base64url 编码；原始 token 只在会话创建成功时返回客户端，不写入数据库、幂等回执或日志。服务端按摘要查找，并同时校验到期、撤销和经营账号启用状态。跨设备登录产生独立会话，最终都关联同一经营账号。

会话不是业务历史。具体有效期以接口及运行配置为准；退出可撤销当前会话，账号停用使全部会话立即失去权限。清理到期会话不删除菜品和周菜单。

### 2.3 菜品 `dishes`

| 字段 | 类型与规则 |
| --- | --- |
| `id`、`merchant_id` | UUID 主键及所属经营账号外键，非空 |
| `name` | text，保存经去除首尾空白、Unicode NFC 规范化后的菜名 |
| `category` | text，仅 `meat`、`vegetable`、`soup` |
| `active` | boolean，是否可用于新生成、换入及恢复隐藏汤 |
| `version` | integer，正数；每次成功修改递增 |
| `created_at`、`updated_at` | timestamptz，服务端记录 |

菜名唯一性覆盖启用和停用的全部菜品。重复输入提示已有条目；不能通过新建同名菜代替恢复停用菜。`name` 使用确定的逐字符比较（PostgreSQL `COLLATE "C"`），与 `merchant_id` 组成唯一键，不另存一份内容相同的规范化名称列。规范化不做繁简转换、拼音映射、大小写折叠或模糊合并；同一批次也按该规则检重。分类建议不持久化，只有桃子确认后的菜名和分类入池。

本版停用是软操作，不提供单菜硬删除。修改菜名或分类递增该菜版本，但不修改已保存周菜单中的快照。菜品所属账号不可修改。

### 2.4 周菜单 `week_plans`

| 字段 | 类型与规则 |
| --- | --- |
| `id`、`merchant_id` | UUID 主键及所属经营账号外键，非空 |
| `week_start` | date，必须为周一；与 `merchant_id` 组成唯一键 |
| `structure` | JSONB，严格包含非负整数 `meat`、`vegetable`、`soup` |
| `meals` | JSONB，恰好 14 项，按本周周一至周日、每天午餐后晚餐排序 |
| `confirmed_at` | timestamptz，可空；只表示保存版本已确认，不表示发到微信 |
| `version` | integer，正数；每次成功保存递增，重放同一幂等请求不递增 |
| `created_at`、`updated_at` | timestamptz，服务端记录 |

同账号同一周只有一份当前记录；首版不保留每次编辑的独立版本表。`version` 用于并发保护，不能据此承诺可逐版撤销。历史周的当前记录和其菜名快照按最终数据保留政策保存。

餐次内容示意，实际数组包含完整的 14 项：

```ts
type Meal = {
  date: string;                     // YYYY-MM-DD，位于目标周
  mealType: 'lunch' | 'dinner';
  enabled: boolean;
  soupOmitted: boolean;
  meat: Array<{ dishId: string; name: string }>;
  vegetable: Array<{ dishId: string; name: string }>;
  soup: Array<{ dishId: string; name: string }>;
};
```

分类由菜位所在数组表达，属于保存快照。无需在每项再存一份可能矛盾的 `category`。同餐各数组合并后 `dishId` 不得重复；不同餐可使用相同菜品。

- 跳过的餐次为 `enabled: false`，三个数组为空且 `soupOmitted: false`。
- 所有生成预览和已保存的启用餐次，每类数组长度均等于周结构中对应数量；普通保存与保存并确认同样拒绝缺位（Q2）。某类可用菜不足填满一餐时，整个生成失败并返回所需/可用数量，不产生部分预览。不同餐可复用菜品；未改动历史快照的可用性按第3节处理，不能因菜池后来停用而把原快照算成缺位。
- 去汤只把 `soupOmitted` 改为 `true`，保留原 `soup` 数组以便恢复；展示和菜单文字均不输出隐藏汤。周汤数量为 0 时数组为空，且不得设为去汤状态。
- 单餐去汤、恢复不改变周结构、荤素数组或其他餐次。原汤失效时按功能规格第2.2节提示重新选齐；服务端不静默恢复停用或不同类菜品。
- `confirmed_at` 与内容同一事务写入。请求 `confirm: true` 通过完整性校验后，若最终规范快照与当前保存内容一致且原已确认，则保留原确认时间；否则设为服务端当前时间。`confirm: false` 设为空。相同幂等键重放仍返回原结果，不参与新确认。确认或复制、发到微信后均可进入编辑（Q3）；进入编辑只创建本地草稿，不清除服务器确认时间，成功普通保存才清空，或通过保存并确认直接记录新版本的确认时间。

已生成菜单改周结构（Q1）时，客户端先提示将覆盖整周的换菜、逐餐去汤等调整，桃子确认后才请求重新生成。取消或生成失败保留原编辑内容和保存记录；成功只替换本地预览，仍须显式保存才修改服务器记录。复制菜单不改变 `confirmed_at` 或 `version`，不写分享历史；修改后从最新保存快照重新生成文字，旧微信消息不会自动更新、由桃子自行通知；按用户最新反馈，界面不再展示相关解释提示。

### 2.5 写入回执 `mutation_receipts`

| 字段 | 类型与规则 |
| --- | --- |
| `merchant_id`、`idempotency_key` | UUID，组成主键；key 为客户端为一次写入生成的 UUID |
| `request_hash` | bytea，32 字节；方法、规范化路径、契约规定的规范 JSON 请求体的 SHA-256 摘要 |
| `response_status`、`response_body` | 成功响应的 HTTP 状态码及 JSONB 内容；不含凭据 |
| `created_at`、`expires_at` | timestamptz，创建后保留 24 小时 |

回执覆盖菜品批量新增、菜品修改和周菜单保存，不用于微信登录、生成预览或读取。同账号同 key、同摘要重试时返回原成功响应；同 key 不同摘要返回冲突。不同接口使用相同 key 也会冲突，因此客户端不得跨操作复用 key。

只持久化成功响应，业务写入和回执必须同事务提交。失败事务不留下成功回执；已过期回执不能继续保证重放，客户端遇到超过窗口的未知结果，应先重新读取记录核对，再决定是否发起新操作。24 小时是技术去重窗口，不是菜品或菜单的保留期限。

## 3. 写入 DTO 与快照验证

周菜单写请求包含 `baseVersion`、`rebuild`、`confirm`、周结构和餐次内容。客户端只提交各分类数组中的菜品 UUID；`name`、所属账号、保存版本和时间由服务端产生，不能接受客户端伪造快照。

默认 `rebuild: false` 时，按「日期、午晚餐、分类、数组索引」对比当前保存记录：

1. 原位置 `dishId` 未变，且不是从隐藏汤恢复为显示汤时，保留已保存的菜名和分类快照；之后菜池改名、改分类或停用不妨碍保存其他菜位的调整。
2. 新增或换入的 `dishId` 必须属于当前经营账号、仍启用且当前分类匹配；名字取当前菜池，不取客户端值。菜位换位置也算换入。
3. 从 `soupOmitted: true` 恢复为 `false` 时，须重新验证该餐所有汤均当前可用且同类，写入其当前名字；有失效项则原子拒绝该次保存，不能悄悄留下部分结果。
4. 首次保存和 `rebuild: true` 的整周重排，全部菜位都按当前菜池验证并重建快照。已有周改变结构必须标记重建，否则以400 `INVALID_REQUEST` 拒绝；客户端按 Q1 先完成覆盖提醒、确认和整周预览。`rebuild` 表示快照验证方式，不是已保存状态，也不能替代客户端的覆盖确认。

对旧快照的保留仅适用于从服务端当前版本继承的同位置菜位。不能以 `rebuild: false` 绕过账号边界、日期范围、数组数量或同餐不重复校验。

## 4. 数据库约束与索引

数据库负责不可绕过的主键、外键、唯一性和基础形状约束；共享契约及服务负责完整 14 餐、日期配对、分类数组、快照和当前菜池校验。SQL 样例只说明必要约束，完整迁移由实施任务交付：

```sql
-- merchants
CHECK (singleton IS TRUE), UNIQUE (singleton), UNIQUE (app_id, openid)
-- dishes
UNIQUE (merchant_id, name), CHECK (version > 0),
CHECK (category IN ('meat', 'vegetable', 'soup'))
-- week_plans
UNIQUE (merchant_id, week_start), CHECK (EXTRACT(ISODOW FROM week_start) = 1),
CHECK (version > 0), CHECK (jsonb_typeof(structure) = 'object'),
CHECK (jsonb_typeof(meals) = 'array' AND jsonb_array_length(meals) = 14)
```

业务表的 `merchant_id` 均为真实外键；所有业务查询都以会话解析出的账号限定范围，不能只按客户端提供的 UUID 查找。餐次 JSON 中的 `dishId` 不是数据库外键，因此写入验证和停用代替硬删除必须同时实施；不能把一个 JSON 字段的存在当成已经具备引用完整性。

| 索引 | 用途 |
| --- | --- |
| `dishes (merchant_id, name)` 唯一索引 | 全账号菜名检重及批量导入冲突 |
| `dishes (merchant_id, active, category)` | 菜池列表和可用候选 |
| `week_plans (merchant_id, week_start)` 唯一索引 | 按周读取与并发首次保存保护 |
| `sessions (token_hash)` 主键；`sessions (merchant_id)`；`sessions (expires_at)` | 认证、撤销账号会话及过期清理 |
| `mutation_receipts (merchant_id, idempotency_key)` 主键；`mutation_receipts (expires_at)` | 安全重试及过期清理 |

不为嵌套餐次建立 GIN 索引，首版按账号和周整份读取；不建尚无查询需求的菜品被使用次数或分享计数。

## 5. 事务、冲突与重试

所有菜品及周菜单写事务采用统一顺序。通过锁定经营账号行，将一个账号的写入短暂串行化，足以覆盖单账号首版；读取不持有该写锁。

1. 认证后开始事务，取得该 `merchants` 行的 `FOR UPDATE` 锁，再确认账号和会话仍有效；所有修改菜品可用性或分类的入口必须遵守此锁顺序。
2. 检查未过期幂等回执：相同请求直接返回原结果；摘要不同则返回冲突。已过期同 key 的行在锁内清除，不能因后台尚未清理而误判为有效回执。重放判断先于版本与当前菜池业务校验，避免成功请求重试时被自己的新版本拒绝。
3. 读取待修改实体，校验版本。周首次保存要求 `baseVersion: 0` 且无已有周；后续要求与当前版本相等。菜品修改同样使用版本条件。
4. 在锁保护下完成批次检重、当前菜池和快照校验；写实体、递增版本、写成功回执，再提交。整批新增全部成功或全部回滚。
5. 提交成功后才发送成功响应。提交前异常回滚全部更改；提交结果因断网未知时，客户端保留原 key 重试，不换 key 再创建。

该锁使「校验菜品可用 → 保存菜单」之间不会插入同账号的停用或改分类。所有写操作先锁账号，再读写实体及回执，避免菜品和周菜单采用反向锁顺序。事务内不请求微信、不调用外部分词或分类服务，不等待用户交互。

更新仍应带 `WHERE version = :baseVersion` 并检查受影响行数；首次周保存依赖唯一约束兜底，冲突返回 HTTP 409。禁止旧设备强制覆盖；错误返回当前版本等必要元信息，前端保留未保存内容并引导重新读取。

## 6. 输入保护与数据生命周期

以下是可调整的初始工程保护值，用来约束校验、内存和请求体，不代表用户实际规模或产品扩容承诺；修改时必须同步契约和测试。

| 对象 | 初始上限 |
| --- | --- |
| 菜名 | NFC 规范化后 1～60 个 Unicode 码点 |
| 单次录入 | 200 个非空菜名 |
| 每账号菜池 | 1,000 条，包含停用菜；恢复已有菜不增加条数 |
| 周结构 | 每类 0～10，合计 1～20；汤可以为 0 |
| HTTP 请求体 | 128 KiB，按传输字节计数，解析前限制 |

备份必须一致地覆盖账号关联、菜池、周菜单及其中的历史快照；恢复校验包括同周唯一、菜位快照、账号归属和被停用菜的历史引用。会话和幂等回执是短期运行数据，恢复后撤销旧会话、清理失效回执，不能用旧 token 自动恢复授权。

最终业务保留期限、备份频率与期限、恢复时间和可接受数据损失窗口，仍属于上线前必须确认并演练的事项。本文没有宣布永久保存，也没有宣称备份恢复已经通过。

退出删除应覆盖经营账号关联、会话、菜品、周菜单、含成功响应的回执、日志和备份。在线数据删除可使用受控事务按外键依赖清理；备份处置及恢复后防止数据重新出现须有独立可核查记录；最终方案见 TECH-SPEC 第7节。不得以备份自然到期替代项目已承诺的退出删除。保留该记录所需的最少信息及期限由退出流程确定，不为此预建顾客或审计业务系统。

部署密钥及数据库连接凭据留在运行环境。结构化日志只记录请求标识、接口、结果及必要错误信息，不包含 bearer token、微信秘密、完整菜单或批量菜名正文。
