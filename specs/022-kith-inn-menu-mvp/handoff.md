## 1. 当前目标和已确认事实

目标产品是**微信小程序**。首版只有桃子使用：维护菜品池 → 设置每周荤素汤数量与午晚餐 → 生成/换菜/逐餐去汤 → 保存回看 → 复制指定餐次文字到微信。订餐继续在微信处理；对账、长期申请、顾客订单、份数及配送不在首版。

用户已确认微信小程序创建好了。后续接入已有小程序，核对 AppID、现有权限、服务端密钥配置与合法请求域名，不重复注册；目前尚未由 Agent 核验这些平台配置，也未验证真机流程。小程序的创建不等于本版业务代码已经实现。

用户已选定“1a，2a，3a”：改周结构须提示覆盖并确认整周重排；缺菜不足一餐则整次不生成；确认/分享后可继续修改、保存和重新复制，由桃子通知邻居。正式规则和完整验收只维护在下列规格，不要重新询问这三个问题。

1. 读取有效规格并核对当前 Git 状态，将本地新版材料安全带入实际实施基线；使协作者能够访问同一版本的规格，再关联实现 Issue。发布文档、PR、合并及部署按本次实际授权和仓库规则执行，不把先前旧文档 PR 的单次合并授权扩展为新产品上线授权。
2. 按 `$github-issue-workflow` 查重、组织近期可验收成果。不要把24个编码任务逐条变成 Issue，也不要把10个 PR 当成10个必建 Issue。
3. 建议近期成果分组：**桃子安全建立和维护菜品池** → **生成、调整并可靠保存一周菜单** → **复制保存的一餐菜单到微信** → **完成真机试用及恢复删除验证**。这是建单建议，尚无实际 Issue 编号；每个 Issue 可覆盖 plan.md 中多个有依赖的小 PR。
4. 优先跑通第一个实施 Issue，再按依赖扩大并行。Issue 正文记录目标、范围/非目标、当前规格、依赖和可操作验收；执行记录关联实际主要任务、分支、PR 和验证证据。
