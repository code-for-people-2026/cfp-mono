# 账号、体验版与正式版调研

2026-10-09 最新范围：三位测试者各有独立测试店，菜品、周菜单、历史和生成参考互不混用；正式环境单独部署，只预置桃子店铺。只有明确授权加入同店的成员才共享数据。无公开入驻、选店或顾客端。本地成员迁移与隔离自动化已通过；云端仍是旧单身份版本，真实同事授权及手机验收尚未执行。

调研日期：2026-10-06。本文保留账号、版本与产品例子的调查依据；本日后续已确认单店多成员，最终决定见第5节，早期一人一空间建议不再执行。当前代码/云端未改。

## 1. 先分清四件事

| 概念 | 决定什么 | 本项目的证据与边界 |
| --- | --- | --- |
| 微信平台项目成员 | 谁可参与小程序开发、运营等平台操作，具体体验权限以后台为准 | 主任务本轮用户截图显示同事已有开发者、运营者权限；无需把“重新添加项目成员”当作默认解决方案。截图是本次后台状态证据，不代替完整平台权限规则 |
| 小程序版本 | 当前运行的是哪种小程序版本 | Taro 官方 API 将 `envVersion` 定义为 `develop`、`trial`、`release`；这不是业务商户数量字段。[Taro.getAccountInfoSync](https://docs.taro.zone/docs/apis/open-api/account/getAccountInfoSync) |
| 后端部署环境 | 请求发给哪套 API、读写哪个数据库 | 当前前端读取编译配置中的 API 地址；服务端另读数据库配置。微信版本名称没有替本项目选择或隔离阿里云数据库。[前端配置](../../apps/kith-inn-miniapp/config/index.ts)、[API 客户端](../../apps/kith-inn-miniapp/src/lib/api.ts)、[服务端配置](../../apps/kith-inn-api/src/config.ts) |
| 业务身份与数据空间 | 谁能登录、能看和修改谁的菜池与菜单 | 当前业务只接受一个预先配置的微信身份，数据库也只允许一个商户记录。[会话实现](../../apps/kith-inn-api/src/sessions.ts)、[初始迁移](../../apps/kith-inn-api/migrations/0001_initial.sql) |

因此，同事已经是项目成员，并不自动使其成为街坊味的业务经营者。当前代码没有读取微信项目成员名单；即使能打开小程序，业务登录仍会经过自己的身份检查。[会话实现](../../apps/kith-inn-api/src/sessions.ts)

微信发布与成员权限的完整官方规则本次未能直接核对：受阻的微信开发文档页面及域名未再次访问，也未通过其他工具或代理绕过。上述 Taro 资料仅用于核对 API 的版本字段；不以腾讯云社区转载、微搭或 TCMPP 文档代替标准微信小程序的发布机制。审核、公开访问范围和特定角色体验权限，仍以本小程序当前后台及可核对的微信官方说明为准。

## 2. 修订前“一位经营者”的来源与现有实现

- 修订前 FR-01/plan 明确限定仅桃子身份登录、无公开注册（见[修订前规格](https://github.com/code-for-people-2026/cfp-mono/blob/7b42bc7b96201496de4bd055659e8b0686ba2bfd/specs/022-kith-inn-menu-mvp/spec.md)）。当前有效规格已改为[单店多成员](spec.md)，实现仍未更新。
- `Sessions.login` 只接受配置的 `ownerOpenId`，其他身份返回无经营权限；会话校验也重复确认该绑定。[sessions.ts](../../apps/kith-inn-api/src/sessions.ts)
- `merchants.singleton` 是必须为真的唯一字段，整个数据库最多一条商户记录；菜品、周菜单与会话通过 `merchant_id` 归属这条商户记录。已有 `merchant_id` 不代表已实现多用户。[0001_initial.sql](../../apps/kith-inn-api/migrations/0001_initial.sql)
- 已有商户记录后，只修改环境变量也不能切换经营者，登录会核对库内原绑定并拒绝不匹配身份；现运维说明要求保留测试数据，正式环境使用独立数据库和身份配置。[sessions.ts](../../apps/kith-inn-api/src/sessions.ts)、[运行手册：微信身份绑定](../../apps/kith-inn-api/deploy/KITH_INN_RUNBOOK.md)

“产品先服务桃子这一位种子用户”是推出顺序；“整个库只能一位经营者”是数据与登录规则。修订前规格和现有实现采用后者；当前新规格已区分店铺与成员。当前限制的直接来源是这些产品和代码决定，不能解释成由“正式版”这一名称强制产生；仅发布正式版也不会使现有实现自动支持多商户。

## 3. 体验与正式发布不自动隔离业务数据

当前 `createKithInnClient` 使用 `TARO_APP_KITH_INN_API_BASE_URL` 选择服务地址，本地会话缓存键也包含该地址；没有按 `envVersion` 自动选择服务的逻辑。服务端使用 `KITH_INN_DATABASE_URL` 选择数据库。因此，在两份前端都指向同一 API、同一后端数据库的情况下，它们会读写同一业务数据空间；改变版本标签本身不会复制或分隔数据库。这是对本项目代码的推导。[API 客户端](../../apps/kith-inn-miniapp/src/lib/api.ts)、[服务端配置](../../apps/kith-inn-api/src/config.ts)

建议用同一套代码和业务账号规则分别部署 staging 与 production，通过配置选择各自 API、数据库和允许身份；明确隔离数据库后再用于测试与正式使用。两套环境可配置不同经营身份，但当前单商户实现仍是每个环境的数据库最多一个商户。现有运行手册已经区分测试身份与正式桃子身份，并要求正式环境使用独立数据库；本次未核验生产环境是否已建立。[运行手册](../../apps/kith-inn-api/deploy/KITH_INN_RUNBOOK.md)

不建议为同事临时创建一套“体验版允许多人、正式版只允许一人”的业务逻辑。先确定最终账号规则，再让体验与正式使用同一规则，测试数据和正式数据由部署配置隔离。这是本次工程建议，不是已落地配置或微信平台规定。

## 4. 两个官方产品例子

| 产品与适用场景 | 官方说明的做法 | 对本项目有用的区别 |
| --- | --- | --- |
| 有赞：商户与连锁门店 | 员工先注册自己的有赞账号，再由管理者选择所属店铺及角色；同一人可管理多个店铺，在同一店铺可具有多个角色；删除员工后其无法继续访问店铺 | 人的身份、店铺数据空间和成员权限是分开的；多人管理同一店与多人各自拥有不同店，属于不同关系。[员工管理使用教程](https://help.youzan.com/displaylist/detail_5_5-2-44011) |
| Plan to Eat：家庭排餐 | 同一账号可跨平台、多设备使用，并允许同一家庭成员共享登录。家庭共享者共同访问菜谱、排餐和购物清单 | 家庭可以围绕同一套数据协作；这个例子不能推导出互不相关的经营者应共用数据。[官方 FAQ](https://www.plantoeat.com/tour/frequently-asked-questions/)、[家庭共享说明](https://www.plantoeat.com/blog/2019/07/sharing-plan-to-eat-with-your-household/) |

Plan to Eat 的家庭共享说明发表于 2019 年；本次同时核对了当前官网 FAQ，仍有相同共享方式。其条款把账号共享范围限定为本人及家庭，明确排除向同事提供账号密码，因此这里只作为家庭排餐的数据共享例子，不推荐拿它的登录方式做商户员工授权。[Plan to Eat Terms：Subscription Services](https://www.plantoeat.com/legal/terms/)

以上只能证明这两个产品实际存在两种模式，不构成“所有排餐工具”或“全行业通常如此”的结论。

## 5. 后续已确认决定：单店、多授权经营成员

用户补充未来要在小程序内为桃子提供顾客点餐，随后确认：当前服务桃子一个店铺，多位经店主授权的经营成员使用各自微信身份，共同维护同一菜品池、菜单和历史。“每人一份独立经营数据”的早期提议不作为当前要求，不建设多商户入驻或选店。

同事先在独立测试店试用，共享测试数据；测试与正式 API/数据库隔离。微信平台项目成员权限不自动转为店铺经营权限。授权或撤销经店主确认，由受控维护流程执行，首期不增加成员管理界面。

未来顾客默认进入桃子店铺，明确显示店名；只可访问公开菜单及自己的订单。经营入口隐藏且后端拒绝越权。顾客账号、公开菜单与订单接口留到后续，不恢复旧订单项目。

[PRD](../../docs/kith-inn/PRD.md)、[功能规格](spec.md)、[数据模型](data-model.md)与[实施计划](plan.md)已按最终决定同步。当前实现依然单身份；后续新增成员迁移须保留原店铺ID、原身份及全部菜品/菜单，验证双成员共享、版本冲突、撤权和未授权拒绝。本次未修改代码、迁移数据库或开放云端权限。
