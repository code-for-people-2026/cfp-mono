# 接口契约与行为校验

版本：0.2 · 2026-09-20 · 状态：Q1～Q3 已按用户选择 1A、2A、3A 确定；接口及数据规则已更新，共享契约已实现并自检，待评审；服务尚未实现。保留 Q 编号用于决策追溯。

机器可读契约：[openapi.json](openapi.json)（OpenAPI 3.1 / JSON Schema 2020-12）；示例：[examples.json](examples.json)；字段存储映射：[data-model.md](../data-model.md)。`packages/kith-inn-contracts` 已承载 Zod schema 与推导类型，前后端共同使用。OpenAPI 描述对外协议；Zod 对22个命名组件及解析后的分页参数提供严格校验；日期/周一、14餐顺序、数量/去汤/重复 ID 等静态跨字段规则已校验。HTTP 层仍须匹配路径周一和首餐日期、解析并拒绝重复 query 参数；权限、菜品当前可用性、历史快照继承、结构变更和版本冲突仍由后续事务实现。共享包通过不等于真实 API 已接通。

## 1. 接口范围

基础路径 `/api/kith-inn`，JSON、HTTPS。除登录和不含业务数据的存活/就绪探针外，均须 `Authorization: Bearer <token>`。全部响应 `Cache-Control: no-store` 和服务端生成的 `X-Request-Id`；未声明字段、重复 query 参数和不支持的 Content-Type 均以400 `INVALID_REQUEST` 拒绝。空体接口拒绝额外请求体（400）；任何请求体超过128 KiB 均可返回413。

| 方法与相对路径 | 行为 | 写入与去重 |
| --- | --- | --- |
| POST `/sessions/wechat` | 微信 code 换成本服务会话，仅预先绑定的桃子可成功 | 登录失败重新取 code；不持久缓存原始 token 响应 |
| DELETE `/sessions/current` | 撤销当前设备会话，返回204 | 再次调用可能401，客户端均清除 token；不影响其他设备 |
| GET `/dishes` | 返回全部菜品，含停用，最多1000项 | 只读；用于维护、候选过滤和恢复汤 |
| POST `/dishes` | 确认新增1～200道菜，单道新增复用该接口 | 整批原子写入，重复名称409整批不写；需幂等键 |
| PATCH `/dishes/{dishId}` | 按版本改名、分类、可用状态 | 需版本和幂等键；不改历史菜单 |
| DELETE `/dishes/{dishId}` | 确认删除单菜，正文 `{baseVersion}`，成功200返回 `{id}` | 需版本和幂等键；不改周菜单快照；同键重试返回成功回执，缺失404、版本冲突409；释放名称和菜池名额 |
| GET `/weeks` | 周一日期倒序摘要，默认12项，最多52项 | `before` 是排他周一游标；结果不含未来空白周 |
| GET `/weeks/{weekStart}` | 读取一个已保存周 | 没有记录返回404，客户端展示设置入口 |
| POST `/weeks/{weekStart}/generate` | 读取当前可用菜池，生成未保存预览 | 不写数据库、不覆盖已有菜单，不需幂等键 |
| PUT `/weeks/{weekStart}` | 首次保存、保存编辑或保存并确认 | 一次事务；需周版本和幂等键；成功统一200 |
| GET `/health`、GET `/ready` | 进程存活；数据库与迁移可用 | 无内部信息、凭据、数据库地址或完整错误 |

分类预览在客户端完成，不增设分类接口。换菜/去汤在本地编辑，候选从已读菜池过滤；保存时服务器重新校验。确认与保存共用 PUT，不存在“先保存失败却确认成功”的第二写入。菜单文字由客户端读取的保存快照格式化，不设公布、解锁、订单、发送或分享记录接口。确认或复制、发到微信后仍可进入编辑（Q3），工具不根据复制动作推断是否已经发送。

## 2. 字段约定

- `weekStart` 是 `Asia/Shanghai` 目标周周一，必须是真实日期；餐次日期范围为周一至周日。ISO 日期按日历运算，操作时间用带时区的 ISO 时间点。
- `meals` 固定14项，依日期升序、每天 lunch 在 dinner 前，不得缺失、重复或越界。未安排餐次 `enabled=false`，三个菜数组必须为空，`soupOmitted=false`。
- `structure` 三类数量0～10，总数1～20。所有成功预览及保存结果中，安排餐次的荤素数量与结构一致；汤被移除时仍保留完整汤数组但 `soupOmitted=true`，展示/复制时隐藏。本周汤为0时数组为空，不能恢复出汤。任一所需分类不足填满一餐时整个生成失败，返回422 `INSUFFICIENT_DISHES` 和各不足分类的所需/可用数量，不返回部分预览（Q2）。普通保存与确认均以400 `INVALID_REQUEST` 拒绝数组缺位，不得用空字符串或同餐重复 ID 凑数。
- 写入数组仅为 `dishId`；响应数组是 `{dishId,name}` 快照。请求禁止指定 `ownerId`、对象 version、操作时间或菜单菜名。分类由数组位置保存。
- 客户端先把原始输入 trim 后 NFC，再形成 API 请求。API 只接受已规范化的菜名，1～60个 Unicode 码点，拒绝控制字符与非规范输入（400）；服务端检查规范化结果必须等于输入，再校验长度，不先对原始输入截断。Zod 实现用 Unicode 码点计数校验，避免 UTF-16 长度与 JSON Schema 不同。按规范化名称全账号唯一，含停用菜。大小写和内部空格不自动改写，不做模糊合并。批内/既有重复或改名冲突返回409和具体名称，整次写入回滚。
- 首次保存 `baseVersion=0,rebuild=true`。已有周提交读取到的版本；重生成后 `rebuild=true`，普通局部编辑 `false`。生成预览不带持久化版本，客户端保留生成前读到的基准版本，保存冲突后不得自动换成最新版本再覆盖。
- 同位置相同 ID 的普通编辑保留原名称与分类快照；新增、换入、恢复隐藏汤或 `rebuild=true` 都必须按当前菜池重新核对归属、分类和可用性。已有周结构变更必须 `rebuild=true`，否则400 `INVALID_REQUEST`。Q1 允许改结构，但客户端须先提醒将覆盖整周换菜和逐餐去汤等调整，桃子确认后才生成；取消或生成失败均保留原编辑和保存记录，成功只替换本地预览，显式保存才更新服务器。
- `confirm=true` 保存并设置确认时间；false 是普通保存并清空 `confirmedAt`。Q3 允许从已确认菜单进入编辑；进入编辑不写服务器，取消或保存失败保留原确认时间，成功普通保存才清空，也可直接保存并确认。已经确认且内容未变的再次确认返回原确认时间，不制造业务上的第二次确认；请求为新键时仍可按写入规则递增技术 version。

JSON Schema 校验不覆盖“周一”“同餐无重复”“数组数量等于结构”“菜品仍可用”等全部规则。Zod refine/纯函数与数据库事务共同落实，不能用通过 OpenAPI 校验替代业务验证。

## 3. 保存事务、冲突与安全重试

所有菜品和周菜单变更在同一账号写锁下执行：验证会话 → 开事务 → 锁定当前 merchant 行并复查 active → 检查幂等回执 → 检查 baseVersion 和业务约束 → 写入完整记录和回执 → 提交 → 返回成功。撤销/退出涉及权限时，事务内复核对应会话仍有效。锁内不请求微信、不调用外部分类服务。菜品变更也取相同账号锁，防止菜单验证可用后、提交前被另一请求停用。

每次明确写入生成 UUID `Idempotency-Key`。去重范围是当前账号+键，请求摘要包含方法、规范路径和规范 JSON 请求体（对象键递归排序、数组顺序保留），不包含 Bearer token。不同会话访问同一经营账号也能重试同一操作。

- 同键同摘要且回执未过期：返回原成功状态和原响应，包括当时的版本；不再次写入，不宣称这是当前最新版本。
- 同键不同摘要：409 `IDEMPOTENCY_KEY_REUSED`，不得把原响应套给新操作。
- 两个同键请求并发：第二个等待账号锁，随后读到第一份成功回执；第一个回滚则第二个正常尝试。
- 回执只保存成功结果，保留24小时；业务校验失败不占用键。到期后按新提交处理，但仍遵守 baseVersion、同周唯一和菜名唯一约束。客户端不能在24小时后盲目重新提交未知结果，应先重新读取；批量菜名已存在时核对结果而非换新键强行重复。
- 保存失败保留原服务器记录和页面草稿。超时结果未知时暂停新写入，用同键同体重试；确认返回后再允许下一次编辑保存。若会话已过期，重新登录同一账号后继续原请求。
- 不同设备发生 `VERSION_CONFLICT`：保留本地草稿，提示“菜单已在另一处更新，请重新读取后再调整”。重读需明确放弃/保留草稿，不静默覆盖，不实现自动合并。

## 4. 错误及界面处理

统一 `{error:{code,message,requestId,details?}}`。`message` 可读，客户端按 code 决定动作，日志只保留诊断 ID、路由模板、状态和耗时。

| HTTP / code | 必要细节 | 界面与重试规则 |
| --- | --- | --- |
| 400 `INVALID_REQUEST` | 可选 field | 指向输入错误，保留当前编辑 |
| 401 `UNAUTHORIZED` | 不回显 token | 清会话并重新微信登录，成功后读取或安全重试 |
| 403 `FORBIDDEN` | 不回显白名单/OpenID | 提示当前账号未获经营权限，不自动注册 |
| 404 `NOT_FOUND` | 不透露别人的对象 | 首次周展示新建入口；菜品则刷新菜池 |
| 409 `DUPLICATE_DISH_NAME` | names | 修改清单，或到维护页恢复停用同名菜 |
| 409 `VERSION_CONFLICT` | currentVersion，未创建为0 | 重新读取后由桃子调整，禁止自动覆盖 |
| 409 `IDEMPOTENCY_KEY_REUSED` | 无原请求正文 | 客户端停止自动重试，纠正请求标识逻辑 |
| 409 `DISH_UNAVAILABLE` | 可选 field | 刷新候选，保留已有编辑；不能自动替换成另一道菜 |
| 422 `INSUFFICIENT_DISHES` | 非空 shortages，列出各不足分类的 category/required/available | 整个生成失败；补菜或改结构后重试，保留原编辑和保存记录，不显示部分预览（Q2） |
| 422 `LIMIT_EXCEEDED` | field | 告知输入或菜池限额，不截断 |
| 413 `PAYLOAD_TOO_LARGE` | 无正文回显 | 缩小批次；不自动拆批造成部分写入 |
| 429 `RATE_LIMITED` | Retry-After | 到期后重试，保留写入键和请求体 |
| 502 `WECHAT_LOGIN_FAILED` | 无微信原始响应 | 重新取一次性 code，避免重复消费旧 code |
| 503 `SERVICE_UNAVAILABLE` / 500 `INTERNAL_ERROR` | requestId | 保留草稿；写入结果未知时同键重试或重新读取 |

具体不存在资源和不属于账号的资源统一404；会话本身不是桃子权限则403。生产所有业务接口无 mock 回退，数据库失败不能返回临时生成的“已保存”结果。

## 5. 排菜与文本的可验证规则

生成前先检查每个所需分类能否填满一餐；任一分类不足则一次列出全部不足分类并失败，不开始返回部分结果。通过后按日期、午晚餐、荤素汤依次填充。每类先从本周尚未使用的合法菜中随机取；未用菜耗尽后，从本餐未选菜中取上一次出现在最早餐次的菜，同优先级用可注入随机源抽取。记录最近出现的餐次序号，使重复尽量隔开，不宣称得到数学最优菜单。只考虑当前周，不额外读取其他周或设隐藏忌口规则。

换菜过滤条件：active、分类一致、不等于当前菜、不与本餐其他菜 ID 重复。随机在合法候选中抽取，手选按名称排序；当前周已用过不等于禁止候选。原菜的可用性变化不导致未修改历史菜位自动重排。

文本格式固定为下列顺序，可在试用后调整排版，不增加状态：

```text
2026年9月23日（周三）午餐
荤：红烧肉、清蒸鱼
素：清炒时蔬
汤：紫菜蛋花汤
```

标题始终包含年份，避免跨年回看混淆。某类为0则不输出该行；去汤不输出汤行。每行从保存快照生成，不从最新菜池反查菜名。客户端须校验服务端响应，通过后才供显示与复制；输出不得带 token、内部 URL 或数据库 ID。

确认或分享后改菜，须先成功保存，再从最新保存版本重新生成文字并复制；不能复用上次复制的文字或把未保存草稿当成对外菜单。复制入口重新读取已保存周，若读取失败则保留编辑并提示重试，不使用旧版本宣称是最新。按用户最新反馈，界面不展示旧微信消息/通知邻居的解释提示；复制成功仅表示已写入剪贴板，不锁定菜单、不改变确认时间或版本，不记录是否发群（Q3）。

## 6. 最小契约验证

本次提供可重复执行的 [check_contract.py](check_contract.py)（Python 3.9+）：检查 OpenAPI 3.1、内部引用、示例请求/响应与拒绝样例。不安装仓库业务依赖，不请求真实 API。可用独立临时环境运行：

```sh
python3 -m venv /tmp/kith-contract-check
/tmp/kith-contract-check/bin/python -m pip install openapi-spec-validator==0.7.2 jsonschema==4.25.1
/tmp/kith-contract-check/bin/python specs/022-kith-inn-menu-mvp/contracts/check_contract.py
```

实现阶段至少再加以下有意义的行为验证：

1. 周一/跨年/闰日、14餐唯一且有序、未安排餐次为空；结构为0汤可保存。
2. 菜足/跨餐复用/连一餐不足，及随机源固定后的结果；同餐永不重复。
3. 换一道或去汤前后深度比较，除目标菜位或标记外其余内容一致。
4. PostgreSQL 真实事务验证两设备 CAS、同周首次并发、同键并发重试、提交中断回滚。
5. 菜品停用后旧快照不变，新换入/恢复失败；普通保存不强制替换未动历史菜位。
6. 微信换码缺省 errcode 或 errcode=0 且 openid 有效可进入白名单校验；非零/缺失 openid/外部失败不授权；非桃子请求与伪造归属被拒绝。
7. 菜名首尾空格、组合重音和 Unicode 码点边界：界面先规范化，API拒绝非规范输入，不截断；新的幂等键对未改动的已确认快照再次确认，保留原确认时间。
8. Q1：已有换菜和周三、周五去汤时改周结构，必须先看到覆盖提醒；取消及生成失败均深度比较原编辑和服务器记录不变；成功只更新预览，保存前另一设备仍读到原版本。
9. Q2：需要两荤但仅一道可用时，返回422及 `required=2,available=1`，响应不含部分菜单；荤、汤同时不足时两项都列出。普通保存和保存并确认的缺位请求均400；未改动的停用历史快照仍可保留，不能误判为缺位。
10. Q3：确认后或复制后进入编辑不写服务器；普通保存清除确认时间，保存并确认更新确认时间，取消或保存失败保留原版本。重读后复制新菜名，旧微信消息不随菜单更新，页面不展示相关解释提示；复制失败、复制成功都不写菜单，不存在公布或解锁状态。

更新字段时同时更新 OpenAPI、示例、Zod 和消费者测试。将来如用 Zod 导出 schema，仍需人工维护认证、状态码和 refine 约束；不再另写一份无关联的 TypeScript DTO。
